# Fase 0 — `78d12d1`

**Problema → mudança:**

1. **Install do SW era all-or-nothing** — um 404 em `STATIC_ASSETS` (`addAll`) fazia `install` falhar ⇒ SW nunca ativava ⇒ **Web Push morria em silêncio**.
   - `public/sw.js`: cache por asset com `Promise.allSettled` + catch individual; `skipWaiting()`/`clients.claim()` movidos para dentro de `event.waitUntil(...)`; `caches.match(request, { cacheName: CACHE_NAME })` (antes varria todos os caches); poda **FIFO** no `activate` (máx. 60 entradas, `MAX_CACHE_ENTRIES`); **`CACHE_NAME` `casasync-v4` → `casasync-v5`** (força reinstalação e descarta caches antigos).

2. **`public/manifest.webmanifest` sombreava o App Router** — `publicFolderItems` resolve antes de `appFiles` (`filesystem.js:413-438, 596`). O manifest servido era o quebrado (sem `name`/`start_url`/`scope`/`display`/cores, **7 ícones 404**, app instalado abria como `browser`).
   - **ARQUIVO DELETADO:** `public/manifest.webmanifest`. `src/app/manifest.ts` virou o único (e agora alcançado) — o build exibe `○ /manifest.webmanifest`. `metadata.manifest` em `src/app/layout.tsx` era o mesmo path, nada mudou lá.

3. **`AndroidBackButton` montado 2×** (root layout + `(app)/layout.tsx`) → duplo handler do Voltar ⇒ voltava 2 páginas.
   - Removido de `src/app/(app)/layout.tsx`; mantido no root layout (`src/app/layout.tsx`).

4. **`NativeServiceWorkerGuard` montado só em `(app)/layout.tsx`** → no app nativo o SW continuava registrado em `/login`.
   - Movido para `src/app/layout.tsx` (root). Removido de `(app)/layout.tsx`.

5. **Logout incompleto e com corrida** — Web Push **não era revogada** (`unregisterAllPushSubscriptions` existia, zero call sites): dependente A fazia logout e dependente B no mesmo aparelho continuava recebendo push do A. Além disso, `router.push('/login')` + `router.refresh()` podia redirecionar de volta para o dashboard antes do cookie limpar (refresh disparava o proxy com sessão ainda visível).
   - `src/components/auth/sign-out-button.tsx`: agora chama `unregisterAllPushSubscriptions()` **antes** do `signOut` (a action depende da sessão); `window.location.replace('/login')` (full reload) elimina a corrida.

6. **Sem UI de erro** — qualquer exceção de RSC caía na UI cinza padrão do Next.
   - **CRIADO:** `src/app/error.tsx` (Client Component com a prop `retry` do Next 16.3) e `src/app/not-found.tsx`.

7. **Órfãos em `node_modules`** — `@tanstack/react-query` 5.107.1, `@tanstack/react-query-persist-client` 5.107.1, `@tanstack/query-*` e `idb-keyval` 6.3.0 estavam presentes, **mas fora de package.json e do lockfile** (sinal falso de "o projeto já usa TanStack").
   - Diretórios removidos manualmente do `node_modules` (equivale a `npm ci` para este caso); `node_modules/.package-lock.json` também não os lista.

**Arquivos da Fase 0:** `public/sw.js` · `public/manifest.webmanifest` (deletado) · `src/app/layout.tsx` · `src/app/(app)/layout.tsx` · `src/components/auth/sign-out-button.tsx` · `src/app/error.tsx` · `src/app/not-found.tsx`.

# Fase 2 — Rotas críticas (árvore de trabalho, sem commit ainda)

**Arquitetura aplicada em toda a Fase 2:**

1. **RSC continua carregando** tudo (primeira pintura + SEO interno + HTML) e passa **`initialData`** para o componente cliente.
2. **Leia/atualize pelo query cache**: componentes não usam mais `useState(initialProp)` nem o efeito "prop→estado" de sincronização (todos removidos); o cache é a única fonte da verdade para dados interativos.
3. **Leituras extraídas para Server Actions `*-reads.ts`**, sempre com **`assertHouseAccess(houseId)`** (`src/utils/tenant-scope.ts`): deriva a autorização da sessão (membresia ADMIN ou DEPENDENT) e nunca aceita escopo do cliente. O `list*` retorna o **bundle** completo (uma unidade de invalidação) e é usado como `queryFn` **e** como seed do RSC → sem duplicação.
4. **Realtime (`usePostgresChanges`) → invalida a chave do bundle** (ou faz patch granular no cache no sino/tasks) — sem chamar `router.refresh()` nas listas. Mapa atual: `tasks`/`chest_items` → upsert/delete granular no bundle de tasks; `rewards`/`redemptions`/`suggestions`/`notifications`(fallback) → `invalidateQueries(qk.rewards)`; `achievements`/`dependent_achievements` → `invalidateQueries(qk.achievements)`; `chest_items` → `invalidateQueries(qk.chest)`; sino → patch direto via `cache.upsert/remove` (linhas completas).
5. **Mutações** mantêm as Server Actions existentes (`revalidatePath` legado preservado em paralelo — será removido na Fase 3) com otimista no cache (patch) onde o padrão já existia (`useOptimisticAction` + `upsertTaskInBundle`/`patchRewards`/`patchAchievementsAdmin`).
6. **`use-profile-points.ts` REMOVIDO** (canal Realtime cru, sem `setAuth` — violava ADR-0010). Saldo de pontos agora via `useMyPoints({ queryKey: qk.points(userId) })` com a mesma subscription via `usePostgresChanges` patchando o cache.

**Por rota:**

- **`/tasks`** — `listTasks(houseId)` retorna `TasksBundle { role, houseId, tasks[], chestItems{}, assignees? | creatorNames? }`. Page: chama a action, passa `initialData`. `tasks-admin.tsx` / `tasks-dependent.tsx`: `useTasksBundle`, sync effects removidos, patch granular (`upsertTaskInBundle`/`deleteTaskFromBundle`/`upsertChestItemInBundle`/`deleteChestItemFromBundle`/`patchTasks`), `invalidateTasks()` no lugar de `router.refresh()`.
- **`/rewards`** — `listRewards(houseId)` retorna bundle discriminado (`RewardsAdminBundle`/`RewardsDependentBundle`: catálogo + resgates com views (`dependentName`/`rewardTitle`) + sugestões + `dependents` (ADMIN)). `getMyProfilePoints()` alimenta `useMyPoints` (saldo ao vivo com realtime via `profiles` → `applyMyPoints`). `rewards-admin.tsx` / `rewards-dependent.tsx`: `useRewardsAdminBundle`/`useRewardsDependentBundle`, Realtime → invalidate, otimistas via `patchRewards`.
- **`/achievements`** — `listAchievements(houseId)` → bundle discriminado (ADMIN: achievements + progress (admin pode manipular) + assignees; DEPENDENT: `views[]` já mesclado). `achievements-admin.tsx`: progresso com patch no cache (`applyOptimisticProgress`/`mergeProgressSnapshot`/snapshot rollback via `patchAchievementsAdmin`), Realtime → invalidate. `achievements-dependent.tsx`: `setViews` removido; Realtime invalida; claim com patch otimista + `invalidateAchievements`. `userId` prop removido (via `initialData`).
- **`/chest`** — `listChest(houseId)` → bundle (ADMIN: items + `maxMb` + `usageBytes` + `attachmentsAllowed`; DEPENDENT: items + `attachmentsAllowed`). `chest-admin.tsx` / `chest-dependent.tsx`: sync durante o render e efeitos removidos; Realtime → invalidate; salvar/excluir → `invalidateChest`. `houseName` continua prop (não faz parte do bundle).
- **Sino de notificações** — `listMyNotifications()`; `useNotifications(userId, initial)` + `useNotificationsCache` (`upsert` cronológico, `remove`, `markRead`, `markAllRead`, `clear`). Realtime upsert/delete → patch direto.
- **`/abrir-anexo`** — intocada (superfície de segurança, CSP sandbox); **nunca** cacheável.
- **Proxy/middleware** — intocado (sessão/role continuam lá; proteção não é responsabilidade do cache).
- **`RealtimePointsListener`** — agora também invalida `qk.points(userId)` (mantém `router.refresh()` para o RSC do dashboard).

**Por fim:** `revalidatePath` das actions **permanece** (duplo caminho documentado) — remoção agendada para a Fase 3.

# Riscos e observações

1. **Dual path de invalidação** (`revalidatePath` nas actions + invalidate no cliente): proposital durante a transição; Fase 3 remove os `revalidatePath` cujas rotas foram migradas.
2. **Realtime não cobre** `dependent_stats`, `dependent_punishments`, `comunicado_deliveries`, `house_settings` — estes usam invalidação pós-action (não há hash/dedup por row id no Realtime por falta de publication).
3. **`comunicados`/`punishments` não persistem em disco** por design (`shouldDehydrateQuery` — segurança infantil e tabelas fora da publicação Realtime).
4. **`/rewards` stale**: pontos de perfil global (`approved_by`) usam `staleTime` 60 s padrão; qualquer crédito via actions invalida `qk.rewards`+`qk.points` — o dashboard (RSC) ainda refresca por `router.refresh()` pontual.
5. **Bundles são a unidade de invalidação**: um evento isolado de sugestão refaz catálogo+resgates+sugestões (1 POST, dados pequenos família). Otimização de fetches finos fica para a Fase 3 se necessário.
6. **Bridges prop→state removidas**: `syncedChestItems` (tasks-admin e tasks-dependent), `syncedProp` durante o render (chest-dependent), e os efeitos "sync server prop" de tasks-admin/tasks-dependent e chest-admin.
