# CasaSync Web — Contexto Compacto

App Next.js 16 (App Router em src/) + Supabase, gamificacao familiar multi-tenant: ADMIN (tutores) cria casas, gerencia dependentes; tarefas geram pontos; recompensas gastam pontos. Roles ADMIN/DEPENDENT (caixa alta). Verificacao antes de entregar: npm run lint -> npm run typecheck -> npm run build. lint warnings no-img-element sao esperados (uso deliberado de <img> para URLs publicas do Storage — nao trocar por next/image).

## Stack
Next.js 16, React 19, Tailwind 4, shadcn/ui, lucide-react, Supabase (Auth/Postgres/Realtime/Storage), Web Push (web-push), PWA. Sem testes configurados.

## Arquitetura
1. Proxy (src/proxy.ts -> src/utils/supabase/middleware.ts) substitui middleware (Next 16). Anonimo -> /login; autenticado -> dashboard da role; /tasks e /rewards role-aware. A role e lida so quando decide redirect (needsRole).
2. Pages (server components) buscam dados via src/utils/house.ts + createClient (RSC) e passam props aos client components.
3. Escritas = Server Actions (src/actions/*.ts, use server) retornando ActionResult { ok, error?, data? }. Credenciais (senha/masterPin) nunca em useState — inputs uncontrolled, lidos via FormData(event.currentTarget) no submit. Server Actions de credencial nao podem lancar excecao (Next exibiria overlay com argumentos) — try/catch + ActionResult.
4. Realtime sincroniza via src/hooks/use-postgres-changes.ts (canal + postgres_changes, filter house_id/recipient_id). O hook faz await getSession() + await realtime.setAuth(access_token) antes de assinar (sessao restaurada de cookies conecta como anon e RLS descarta eventos). Ver ADR-0010.
5. Modal (src/components/ui/modal.tsx): portal no body (z-[100]), scroll lock, focus trap Tab/Shift+Tab, fecha no Esc.

## Supabase (3 clientes)
- server.ts createClient() — RSC.
- client.ts createClient() — browser.
- admin.ts createAdminClient() — service role, server-only, nunca importar de client component.
Env vars (so .env.local): NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY, SUPABASE_SERVICE_ROLE_KEY, MASTER_PIN. Sem PIN_PTS (alteracao de pontos usa PIN da casa houses.code).
Auth: emails sinteticos ${username}@admin.casasync / @dependente.casasync, email_confirm: true via service role. DEPENDENT nunca se cadastra sozinho.
Autorizacao sempre derivada da sessao; service-role para escritas que RLS nao cobre (criacao de usuarios, credito/debito de pontos) e leituras cross-role com escopo explicito (ADR-0006).
Controle de casa = membresia house_members.role=ADMIN (criadas e co-geridas via PIN em joinHouseByPin), nao owner_id (so tutor/criador).
Transicoes de status com guard (.in(status, ...)) impedem duplicacao e revertem em falha.
Migracoes SQL nao versionadas (pasta supabase/ nao existe) — aplicadas manualmente. Ja aplicados: colunas de imagem (rewards.active, notifications.image_url/message_id), reward_suggestions, flags extension_*, enum task_status com NOT_DELIVERED+ON_HOLD, tabela notifications + policy + publication, bucket casasync-media (com pasta messages), tabela house_settings (+ policy SELECT por membro), tasks.decay_started_at, tabelas achievements/dependent_achievements, 3 colunas das conquistas (image_url/max_level/level_multiplier), dependent_stats + migracao COMPLETED_TASKS->TASKS_APPROVED. Pendente: tabelas de comunicados (comunicados/comunicado_deliveries — SQL em docs/sql/comunicados.sql). Blocos de SQL em PROJECT_STATUS.md/docs/adr/ sao registro historico.

## Regras de negocio essenciais

- Hierarquia: Admin -> Casa(s) -> Dependente(s) -> Tarefas/Recompensas, isoladas por house_id (RLS) — multi-tenant.
- Ciclo da tarefa: DEPENDENT conclui (COMPLETED); ADMIN aprova (credita), desaprova (COMPLETED->PENDING, sem credito) ou conclui+credita de uma vez (adminCompleteTask, PENDING/IN_PROGRESS->APPROVED).
- approveTask: COMPLETED->APPROVED soma tasks.points em profiles.points; apos COMPLETED a tarefa e imutavel para edicao.
- approveRedemption: PENDING->APPROVED debita points_cost do saldo; rejectRedemption: PENDING->REJECTED.
- Tarefa nao entregue (NOT_DELIVERED): ADMIN marca tarefa atrasada (markTaskNotDelivered, PENDING/IN_PROGRESS->NOT_DELIVERED, guard) e debita tasks.points do dependente (saldo pode ficar negativo). Dependente perde o Concluir mas mantem pedido de adiamento. Penalidade definitiva: aprovar adiamento (resolveTaskExtension) ou alterar prazo (updateTask) reabre a tarefa com tasks.points=0 e status equivalente ao novo prazo (futuro->PENDING), sem devolver pontos. Nao ha Concluir e creditar para NOT_DELIVERED. Ver ADR-0007 (emenda 2026) e ADR-0018.
- Tarefa em espera (ON_HOLD — setTaskOnHold): ADMIN pausa PENDING/IN_PROGRESS/NOT_DELIVERED (guard .in) e a tarefa some da lista do dependente. Pausa descarta pedido de adiamento pendente e, se era NOT_DELIVERED, grava points=0. Reativar (guard .eq('status','ON_HOLD')) volta sempre para PENDING com prazo novo (agora + task_sla.defaultDueDays) e decaimento reiniciado, preservando tasks.points e sem tocar no saldo. UI: botao Colocar em espera (PauseCircle) no card pendente + secao Em espera com Voltar para pendente (PlayCircle); notificacao TASK_ON_HOLD na pausa e TASK_RESTORED na reativacao. expelMember/deleteDependentAccount apagam ON_HOLD como tarefa ativa. Nao altera dependent_stats. Ver ADR-0018.
- Restaurar tarefa aprovada: ADMIN reaproveita APPROVED via restoreTask (APPROVED->PENDING, guard). Preserva dados e nao altera pontos ja creditados; limpa completed_*/flags de adiamento e reinicia prazo para agora + defaultDueDays dias. Ver ADR-0008.
- Decaimento de pontos: tarefa perde pointsPerPeriod a cada periodHours completas desde decay_started_at (criacao ou ultima edicao, fallback created_at), janela capada no due_date, piso 0. tasks.points e a base. Adiamento aceito = novo ciclo a partir do valor corrente (resolveTaskExtension aprovando e auto-aceite do updateTask): pts originais nunca voltam — valor no instante do aceite vira nova base e relogio reinicia (calculado com prazo antigo). updateTask toda edicao reinicia o relogio; restoreTask e reativacao de ON_HOLD tambem reiniciam. Valor corrente creditado na aprovacao (approveTask/adminCompleteTask) e debitado em NOT_DELIVERED (markTaskNotDelivered); reabertura de NOT_DELIVERED nao devolve nada — so zera tasks.points. Configuravel por casa (chave task_decay; default ativo 24h/1pt). UI mostra valor corrente (base riscada quando reduzido) em pendentes/concluidos; aprovadas mostram base.
- SLA de prazo: overdue (agora > prazo) e dueSoon (faltam menos de dueSoonHours horas — limiar absoluto, settings task_sla, default 4; 0 desliga).
- Prazos sempre com fuso: input datetime-local produz hora local sem fuso — cliente converte em instante via datetimeLocalToIso (fuso do dispositivo, client-only) antes de createTask/updateTask; servidor normalizeDueDate rejeita string sem fuso (fail-closed). Exibir hora local de instante em JSX sempre renderizado: usar FormattedDateTime (hora local so apos hidratacao via useSyncExternalStore) — toLocaleString no SSR gera hydration mismatch. Ver ADR-0013.
- Pedido de adiamento: dependente define extension_requested=true + extension_reason (obrigatorio, <=500); ADMIN aprova (botões +1 dia/+3 dias sobre data atual ou futura; em NOT_DELIVERED reabre com 0 pontos, sem devolver debito) ou rejeita (resolveTaskExtension); flags limpas nos dois casos.
- Sugestoes de recompensa: dependente envia; ADMIN aprova -> cria a recompensa real (transicao guardada PENDING->APPROVED com rollback) ou rejeita.
- Desativacao de recompensa: ADMIN alterna rewards.active (setRewardActive); desativada nunca excluida, fica Indisponivel na loja do dependente e requestRedemption rejeita (active=false). So ADMIN reativa; resgates ja resolvidos nao afetados.
- Notificacoes: cada acao relevante grava notificacoes para o outro lado (dependente para acoes do ADMIN; todos os ADMINs membros para acoes do dependente; quem agiu excluido). Registro best-effort (notifyUser/notifyHouse) — falha nao derruba a acao. Gerenciadas pelo destinatario (marcar lida/todas, apagar uma/todas) e lidas comuns apagadas apos readRetentionDays (settings notification_retention, default 5; limpeza lazy por casa da notificacao e excluindo QUICK_MESSAGE). Ver ADR-0009.
- Mensagem rapida (DEPENDENT->ADMINs): sendQuickMessage(text, imageUrl?) — so DEPENDENT; texto <=100 opcional (exige texto OU imagem) e imagem = URL publica do bucket na pasta messages/; capacidade: envia apenas enquanto tiver menos de 2 mensagens proprias acumuladas (lidas ou nao; conta message_id distintos); insere 1 copia por ADMIN da casa com mesmo message_id + 1 copia para o proprio dependente como comprovante ja lido (Mensagem enviada, sem edicao, nao conta na retencao) e envia push aos ADMINs (best-effort, quem agiu excluido). Ao abrir QUICK_MESSAGE no sino o visualizador marca como lida (sem link); retencao por tempo: assim que ao menos um admin abre, grupo inteiro apagado apos readRetentionDays dias (configuravel 1-365, default 5); mensagens nunca lidas por admin ficam armazenadas. Composer no sino so do DEPENDENT (galeria + camera ao vivo getUserMedia com fallback). Constantes em src/utils/quick-message.ts (QUICK_MESSAGE_MAX_CHARS=100, MAX_IMAGE_MB=5, CAPACITY=2, QUICK_MESSAGE_READ_RETENTION_DAYS=5).
- Reset de senha pelo ADMIN: updateMemberPassword (service role, sem email) — qualquer ADMIN redefine a propria senha; redefinir a senha de outros (dependentes ou co-ADMINs) so pelo autor da casa (houses.owner_id); escopo por house_members, senha >=6, sessoes ativas nao revogadas. Ver ADR-0011.
- Alteracao de pontos pelo ADMIN: updateDependentPoints (service role) faz SET absoluto de profiles.points de um dependente exigindo o PIN da casa (houses.code, comparado como joinHouseByPin — trim + uppercase, fail closed); escopo = alvo DEPENDENT de casa que o ator controla; valor inteiro em POINTS_MIN/POINTS_MAX (validatePoints), pode ser negativo. Ver ADR-0012.


## Regras de negocio (cont.)

- Conquistas gamificadas (/achievements, ver ADR-0015): ADMIN cria/edita/exclui conquistas da casa ativa (titulo <=100, descricao opcional, icone de ACHIEVEMENT_ICONS ou imagem — ImageUpload na pasta achievements/, reward_points 0..POINTS_MAX, target_count >=1, metric_type AchievementMetricType (uniao de 8: TASKS_APPROVED, TASKS_REJECTED, REWARDS_CLAIMED, CUSTOM_REWARDS_APPROVED, APP_LOGIN_DAYS, STREAK_LOGIN_DAYS, EARNED_POINTS, MANUAL), flags is_repeatable/is_secret, max_level 1-1000 (so repetiveis; unica=1, server clampa) e level_multiplier 0-100). Progresso derivado de dependent_stats (uma linha por dependente+casa, contadores zerados; ver ADR-0016): dispatcher registerAchievementProgress (mesma assinatura — nunca duplicar caminhos em paralelo): MANUAL->no-op; EARNED_POINTS->soma incremental via syncAchievementProgress (valor corrente creditado, ja com task_decay); demais->incrementDependentStat (lazy insert ou update atomico com guard .eq(column, valor lido) + 1 retry) e depois evaluateAchievements. Todas as chamadas best-effort. Injecoes: approveTask/adminCompleteTask->TASKS_APPROVED (1)+EARNED_POINTS (valor corrente); rejectCompletedTask->TASKS_REJECTED; approveRedemption->REWARDS_CLAIMED; resolveRewardSuggestion aprovado->CUSTOM_REWARDS_APPROVED; registerLoginDay (1x/dia em America/Recife, idempotente, streak) nos renders dependentes->APP_LOGIN_DAYS/STREAK_LOGIN_DAYS; adjustAchievementProgress (ADMIN, conquista MANUAL, botao +1/-1 por dependente em /achievements; positivo concede, negativo revoga o desbloqueio)->MANUAL. evaluateAchievements grava o progresso e trava no objetivo (ADR-0019): repetivel = soma incremental no valor gravado, com teto via applyAchievementProgress (so a 1a ocorrencia usa o contador); unica = min(contador, objetivo) com piso historico; unlocked_at so marcado no cruzamento e quando ausente. current_progress nao capado no banco (UI capa barra em 100%). DEPENDENT resgata (claimAchievementReward, so da propria casa) -> credita direto em profiles.points o valor do nivel atual via achievementRewardAtLevel(reward_points, level, level_multiplier) = round(reward_points x nivel x mult); repetivel: sobe 1 nivel por ciclo, zera current_progress, unlocked_at volta a null — no cap (nivel=max_level) continua repetivel, fica travado pagando a recompensa maxima; nao repetivel so resgata no nivel 1. Guards anti-race no unlocked_at (repetivel)/level (nao repetivel) + rollback da linha se o credito falhar. Conquista secreta (is_secret): card visivel oculto que so revela quando o dependente tem linha de progresso (i.e., ao desbloquear). Sem notificacao ACHIEVEMENT_UNLOCKED (decisao de escopo). Limpeza: excluir conquista apaga o progresso (FK cascade); expelMember/deleteDependentAccount/deleteHouse removem linhas de dependent_achievements (e deleteHouse as achievements da casa). Ver secao no topo do PROJECT_STATUS.md (SQL aplicado — registro historico) e ADR-0015/ADR-0016.

- Comunicados/avisos da casa (/dashboard/admin/comunicados — card na visao geral, sem item na nav): ADMIN cria avisos (titulo 1-120, descricao 1-500, repeats_total 1-100, repeat_interval_days 0-365, >=1 repeat_weekdays, repeat_time HH:mm) que sao publicados (published) e confirmados pelos dependentes da casa ativa. O ADMIN não escolhe a casa: o item nasce na casa ativa e a lista é o acervo dela; pode renomear/trocar o arquivo/excluir. Trocar a casa ativa troca o acervo exibido. O dependente só consulta e abre, com busca por título dos dois lados. Sem pontos, sem resgate e sem notificação; Realtime sim (é catálogo). Sem item na nav de nenhum papel (só o card, nas duas visões gerais). SQL da tabela chest_items em docs/sql/chest_items.sql, a aplicar antes do deploy. Ver ADR-0024.

- Castigo do dependente com 2 níveis: o ADMIN escolhe entre aviso (nível 1, triângulo amarelo — só avisa que o castigo está próximo) e castigo (nível 2, triângulo vermelho — o vigente). A diferença é a cor e o texto; os dois continuam sendo só indicador (ADR-0020, nenhuma escrita em pontos, tarefas ou conquistas) e sem notificação. SQL da coluna level em docs/sql/punishment_level.sql, a aplicar antes do deploy (default 2, sem backfill). Ver seção no topo do documento.

## Convenções críticas de código
- Senha/masterPin nunca em useState/inputs controlados; forms de sucesso chamam reset(). Server Actions de credencial não podem lançar exceção (Next exibiria overlay com argumentos) — try/catch + ActionResult { ok: false, error: genérico }.
- Formulários com campo de senha: <Input suppressHydrationWarning> (extensões de senha causam hydration mismatch).
- Imagens do Storage: <img> direto (não next/image); warnings no-img-element são esperados.
- next.config.ts usa module.exports E export default (legado allowedDevOrigins) — não "consertar".
- tsc depende de .next/types gerado: apagou .next, rode npm run build antes.
- Service worker (public/sw.js): cache-first somente para assets estáveis — STATIC_ASSETS (manifest/ícones) e chunks sob /_next/static/ (hasheados). Qualquer outro GET same-origin (inclusive payloads RSC de router.refresh()/prefetch/Realtime, com header RSC:1) vai direto à rede, sem cache. Não re-ampliar cache-first; bump CACHE_NAME ao alterar o SW.
- Mensagens de commit em português, curtas; commitar apenas quando solicitado.
- Revalidação das actions de casa é FONTE ÚNICA — revalidateHouseContext() em src/actions/houses.ts (constante HOUSE_CONTEXT_ROUTES). Não escrever bloco de revalidatePath novo na action.
- GUARD em TODA escrita em tasks, sem exceção.
- Crédito/débito de profiles.points é sempre com guard: adjustPoints usa .eq('points', valor lido) + 1 retry relendo.
- Feedback imediato nas transições: padrão runTaskTransition(task, buildOptimistic, run, options) em tasks-admin.tsx. pending/startTransition só nos 3 botões do formulário de criação. A regra vale para QUALQUER handler de client component.
- Rollback de update otimista é CONDICIONAL e por id: desfaz só o card que ainda está num valor produzido pelo otimista, via registro (optimisticIdsRef: Set<string>), não por predicado.
- router.refresh() só funciona se o componente sincronizar a prop: TasksAdmin/TasksDependent são montados com key={casa.id}; na mesma casa o refresh re-renderiza o Server Component mas o useState(initialTasks) ignora a prop nova. Por isso ambos têm um efeito que faz setTasks(initialTasks) quando a prop chega, pulado enquanto houver valor otimista.
- Escrita nunca entra no caminho da leitura: tudo que é INSERT/UPDATE/DELETE e roda no render (limpeza lazy de notificações, DELETE do castigo vencido, registerLoginDay) vai para after() do Next 16 (Vercel garante com waitUntil). next dev NÃO executa o callback do after() mas em produção executa.
- Prazos de tarefa SEMPRE com fuso: cliente converte para instante via datetimeLocalToIso antes de chamar as actions, e o servidor (normalizeDueDate) rejeita qualquer due_date sem designador de zona. Exibir hora local de um instante no JSX sempre renderizado? use FormattedDateTime.
- Realtime + RLS exige setAuth: quando a sessão é restaurada de cookies/storage, o socket Realtime pode conectar como anon e o RLS descarta os eventos em silêncio. O hook usePostgresChanges faz await getSession() + await realtime.setAuth(access_token) antes de assinar — nunca remover.
- Busca por combinação de palavras no autocomplete de tarefas (ADMIN) — src/utils/task-normalize.ts: combina as palavras (tags) digitadas, independente da ordem, com no mínimo 1 caractere por palavra. O termo casa com a palavra do título por igualdade, início (prefixo) ou trecho, com qualidades 3/2/1. Só entra sugestão se todas as palavras da busca casarem. searchTasksByWords<T>(query, items, getTitle, limit) genérico, roda em memória (catálogo da casa já está no estado do form) e é useMemo no tasks-admin.tsx. Busca vazia é a única que não sugere. Guard de duplicidade (soft block no client + título normalizado no createTask) continua exigindo igualdade.
