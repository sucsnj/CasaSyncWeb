# CasaSync Web — Diretrizes do Projeto

## 1. Comandos de verificação (não há testes configurados)
- `npm run dev` · `npm run lint` (eslint) · `npm run typecheck` (`tsc --noEmit`) · `npm run build`.
- Ordem antes de entregar: **lint → typecheck → build**. Todos devem passar.
- `npm run lint` emite warnings `no-img-element` **esperados** (uso deliberado de `<img>` para URLs públicas do Storage) — não "consertar" trocando por `next/image`.
- `tsc` depende do gerado `.next/types` (ex: `LayoutProps<"/">` em `src/app/layout.tsx`). Se `.next/` for apagado, rode `npm run build` (ou `next dev`) antes do `tsc` puro.
- **Service worker (`public/sw.js`):** o `fetch` handler faz **cache-first somente para assets estáveis** — `STATIC_ASSETS` (manifest + ícones) e chunks de build sob `/_next/static/` (JS/CSS nomedos por hash). **Qualquer outro GET same-origin passa direto à rede, sem cache** — incluindo os payloads RSC das páginas (o `router.refresh()` pós-ação e o Realtime buscam `/tasks`, `/rewards` etc. com header `RSC:1`). Cachear RSC gravava respostas 200 obsoletas e a UI "piscava" de volta ao dado antigo, demorando a fixar mudanças já gravadas no banco (ver topo do `PROJECT_STATUS.md`). Não re-ampliar o cache-first para navegação nem GETs genéricos; ao trocar o conteúdo do SW, bumpear o `CACHE_NAME` (ex.: `casasync-v4`) para o `activate` limpar caches antigos.
- Rodar `npm run build` antes de `npm run dev` para evitar geração conflitante de `.next`.

## 2. Estrutura e convenções
- Todo o código de app vive em `src/`; alias `@/*` → `./src/*` (tsconfig). Há um route group `(auth)` (URLs `/login` e `/register` sem o prefixo).
- **Next.js 16 trocou middleware por proxy:** a proteção de rotas fica em `src/proxy.ts` (export `proxy` + `config.matcher`, ao lado de `src/app`); a lógica de sessão/role vive em `src/utils/supabase/middleware.ts`.
- `next.config.ts` usa `module.exports` E `export default` (legado com `allowedDevOrigins`). Não "consertar" isso.
- `PROJECT_STATUS.md` é o estado do projeto (requerido ler ANTES de trabalhar e ATUALIZAR ao terminar — funcionalidades, arquivos, decisões, próximo passo).
- Docs complementares (commitados): `docs/schema.md` (snapshot do schema Supabase) e `docs/adr/` (decisões arquiteturais — o "porquê" de padrões como service role/credenciais/proxy/leituras cross-role).
- **Tarefas (ADMIN) — `src/components/tasks/tasks-admin.tsx`:** cards **colapsáveis** com cabeçalho clicável (chip de status/SLA + título + pontos + chevron), **todos recolhidos por padrão** (`expandedIds: Set<string>`). Aplicado a pendentes/concluídas/aprovadas; no card concluído os botões "Aprovar"/"Desaprovar" e no card aprovado o botão "Restaurar" ficam sempre visíveis, fora do toggle. **Mobile:** o título fica na linha de cima e chips/pontos/botões descem para uma linha abaixo (em `sm:` voltam a ficar lado a lado) — não regredir para uma única linha fixa.
- **Notificações:** tabela `notifications` (uma linha por destinatário), helpers em `src/utils/notifications.ts` (`notifyUser`/`notifyHouse`, best-effort), actions em `src/actions/notifications.ts` e sino em `src/components/notifications/notifications-bell.tsx` (cabeçalho). Destinatário = "o outro lado" da ação; **lidas comuns apagadas após a retenção da casa** (settings `notification_retention.readRetentionDays`, default 5, limpeza lazy **por casa da notificação** e **excluindo `QUICK_MESSAGE`** — as mensagens rápidas têm regra própria de tempo). **Mensagem rápida DEPENDENT → ADMIN:** `type='QUICK_MESSAGE'` + `image_url`/`message_id` (colunas **já aplicadas no banco**); compositor no sino só do DEPENDENT (`quick-message-composer.tsx`: texto ≤100 caracteres + 1 imagem ≤5MB da Galeria ou câmera ao vivo via `getUserMedia`); `sendQuickMessage` só DEPENDENT, com capacidade de no máx. 2 mensagens próprias acumuladas (conta `message_id`, não cópias) e **envia push aos ADMINs da casa** (best-effort, quem agiu excluído); ao abrir a mensagem marca lida; **retenção por tempo:** assim que **ao menos um admin** abre a mensagem, o grupo inteiro é apagado após `readRetentionDays` dias (configurável 1–365, default 5); mensagens nunca lidas ficam armazenadas; `cleanupQuickMessages` reescrita para regra de tempo (`src/utils/notifications.ts`). Ver ADR-0009 e seção de mensagem rápida no `PROJECT_STATUS.md`.
- **"Sair" em qualquer tela:** em `dashboard-nav.tsx` o avatar do cabeçalho é um `<button>` que abre um `Modal` "Sua conta" (nome + pontos + `SignOutButton`). Necessário porque o "Sair" do header é `hidden md:block` e o slot extra da bottom nav só existe com `items.length < 4` — sem isso o ADMIN no mobile (4 itens) não conseguiria sair. Não regredir: desktop/bottom nav continuam com seus botões.
- **Pontos só do DEPENDENT:** ADMIN não acumula pontos, então `points` **não** é passado ao `DashboardNav` no layout admin, em `/tasks` nem em `/rewards` (`isAdmin ? undefined : profile.points`). O `DashboardNav` só renderiza o badge "N pts" e a linha de pontos do Modal "Sua conta" quando `points` é número — não reintroduzir `points={profile.points}` fixo.
- **`Modal` (`src/components/ui/modal.tsx`):** renderiza via **portal no `body`** (`z-[100]`), **trava o scroll do documento**, **prende o foco (Tab/Shift+Tab) dentro da janela** enquanto aberto e fecha no **Esc**. Necessário porque o sino vive no header azul (`text-white`/`z-50`) — sem o portal o painel herdava a cor branca e a bottom nav ficava clicável por trás.
- **Upload de imagem em TAREFAS desabilitado (decisão de produto, 2026):** em `tasks-admin.tsx` o `ImageUpload` do form de tarefas (import, estado `taskImageUrl`, bloco JSX e input hidden `image_url`) está **comentado** — a feature foi desligada para **não inflar o storage/banco**. Com o campo removido, `formData.get('image_url')` volta `null` e tarefas novas nascem sem imagem. A coluna `tasks.image_url` e as actions `createTask`/`updateTask` **continuam intactas** e imagens de tarefas **antigas** seguem exibidas nos cards (ADMIN e DEPENDENT). Não "consertar" reativando o upload sem o usuário pedir (ver `PROJECT_STATUS.md`).
- **Exclusão real de conta de dependente (`deleteDependentAccount` em `src/actions/houses.ts`):** só o **autor da casa** (`getOwnedHouse`) exclui a conta **completa** de um membro `DEPENDENT` — limpeza em **ordem explícita** (tarefas ativas, resgates, sugestões, notificações, push subscriptions, storage best-effort via `deleteMemberStorage`, membresias, perfil) e `admin.auth.admin.deleteUser` **por último**. **Histórico da casa preservado:** tarefas `COMPLETED/APPROVED` são **mantidas** apenas desatribuídas (`assigned_to`/`completed_by` → null); resgates resolvidos do dependente são removidos (`reward_redemptions.profile_id` é NOT NULL — sem migração não há como reter o log). **Conta de ADMIN nunca é excluída** (co-gerente expulso: só `expelMember`). UI: em `houses-manager.tsx` o botão do dependente é **"Excluir conta"** (`Trash2`, autor-only, com `Modal` de confirmação) no lugar de "Expulsar"; co-ADMINs seguem com "Expulsar". Ver ADR-0014.
- **Conquistas gamificadas — rota `/achievements` (module novo, 2 tabelas **já aplicadas no banco**):** tabelas **`achievements`** (por casa: título ≤100, descrição, `icon` slug de `ACHIEVEMENT_ICONS`, `metric_type`, `reward_points`, `target_count`, `is_repeatable`, `is_secret`, `created_by`) e **`dependent_achievements`** (uma linha por conquista+dependente: `level`, `current_progress`, `unlocked_at`). Constantes/tipo (`ACHIEVEMENT_ICONS`/`ACHIEVEMENT_METRIC_TYPES`/`AchievementMetricType`) vivem em **`src/utils/achievements.ts`** (módulo puro — client components **não** importam valores de arquivo `'use server'`; foi o bug `ACHIEVEMENT_ICONS.map is not a function`). Actions em `src/actions/achievements.ts` (`createAchievement`/`updateAchievement`/`deleteAchievement` — ADMIN da casa ativa, validação fail-closed; **`registerAchievementProgress(houseId, profileId, metricType, amount)`** chamada **best-effort** no caminho do crédito de `approveTask`/`adminCompleteTask` — amount 1 p/ `COMPLETED_TASKS` ou o valor corrente creditado (com `task_decay`) p/ `EARNED_POINTS`, com lazy insert + update por guard `.eq('current_progress', valor lido)` + 1 retry — concorrência não perde incremento; **`claimAchievementReward`** só DEPENDENT da própria casa, credita em `profiles.points`, repetível faz rollover do progresso e não repetível resgata só no nível 1). **Decisões de escopo:** progresso conta apenas aprovações (não débitos); `EARNED_POINTS` conta só créditos de tarefa aprovada (sem loop com resgates); **sem notificação `ACHIEVEMENT_UNLOCKED`**; conquista `is_secret` aparece como card oculto "Conquista secreta" até o dependente desbloquear. UI: `achievements/achievements-admin.tsx` (CRUD + progresso por dependente; **sem `router.refresh`** — Realtime cobre), `achievements/achievements-dependent.tsx` (barra/pill "N/N"; `handleClaim` otimista + `router.refresh()`), `achievements/achievement-icon.tsx` (`AchievementIcon` + `ICON_MAP`). Nav ganhou o item **"Conquistas"** (`Trophy`) — ADMIN passa a **5** itens, DEPENDENT mantém **4** (o slot extra da bottom nav só existe com `< 4` itens). Limpeza: excluir conquista apaga o progresso (FK cascade); `expelMember`/`deleteDependentAccount`/`deleteHouse` removem linhas de `dependent_achievements` (e `deleteHouse` as `achievements` da casa). Ver seção no topo do `PROJECT_STATUS.md` (SQL pendente) e **ADR-0015**.
- **Configurações da casa (ADMIN) — rota `/dashboard/admin/settings` + card na Visão geral:** tabela `house_settings` (PK `house_id,key`, `value` jsonb), escrita **exclusivamente** por `updateHouseSettings` (`src/actions/settings.ts`, service role + membresia ADMIN) e lida pelos getters cached em `src/utils/house-settings.ts` (`getHouseRewardPricingSettings`/`getHouseQuickMessageSettings`/`getHouseTaskSlaSettings`/`getHouseExtensionRulesSettings`/`getHouseNotificationRetentionSettings`/`getHouseTaskDecaySettings`, fallback aos defaults de `src/utils/settings.ts`). **Sem Realtime** — a propagação depende do `router.refresh()` pós-ação (e das revalidações de `/tasks`, `/rewards`, `/dashboard/dependent` quando `quick_message` muda, e de `/tasks` quando `task_sla`/`extension_rules`/`task_decay` mudam). As configurações alimentam: `approveRedemption` (toggle + faixas do encarecimento em `nextRewardCost` — chave `reward_pricing`); a mensagem rápida (`sendQuickMessage` valida maxChars/capacity; `cleanupQuickMessages` usa `settings.readRetentionDays`; o compositor e a plumbagem bell→nav usam `QuickMessageSettings`, carregada nos call sites DEPENDENT — chave `quick_message`); os prazos de tarefas (`restoreTask`, o prefill do form e o autocomplete usam `defaultDueDays`; o chip "Prazo próximo" de ADMIN/dependente usa `dueSoonHours` — horas restantes até o prazo, limiar absoluto, passado como prop pelas páginas — chave `task_sla`); o adiamento (os botões "Aprovar (+N dias)" renderizam `dayOptions` e `resolveTaskExtension` **rejeita dias fora da lista** — chave `extension_rules`); a retenção do sino (`cleanupReadNotifications` aplica `readRetentionDays` **por casa da notificação**, excluindo `QUICK_MESSAGE` — chave `notification_retention`); e o **decaimento de pontos de tarefas** (`enabled`/`periodHours`/`pointsPerPeriod` — chave `task_decay`; ver §4 "Decaimento de pontos"). Não repassar chaves de settings por parâmetro público — a leitura é sempre derivada da casa da sessão.

## 3. Supabase
- Três clientes em `src/utils/supabase/`: `server.ts` (`createClient`, regras Servers/RSC), `client.ts` (`createClient` browser), `admin.ts` (`createAdminClient` com service role, **server-only** — nunca importar de client component).
- Env vars só em `.env.local` (nomes exatos, `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` — é *publishable*, não `ANON_KEY` — `SUPABASE_SERVICE_ROLE_KEY`, `MASTER_PIN` que valida o cadastro de ADMIN em `actions/auth.ts`); `.env*` está no `.gitignore`, nada disso vive no repo. **Não existe `PIN_PTS`:** a alteração manual de pontos (`updateDependentPoints`) é validada pelo PIN da casa (`houses.code`).
- **Migrações SQL não estão no repo:** a pasta `supabase/` não existe e `supabase/*.sql` é gitignore. Mudanças de schema são aplicadas manualmente no dashboard do Supabase — sem aplicá-las, features falham em runtime. **Quase tudo já foi aplicado no banco:** colunas de imagem (incluindo `rewards.active` e `notifications.image_url`/`message_id` da mensagem rápida), `reward_suggestions`, flags `extension_*`, enum `task_status` com `NOT_DELIVERED`, tabela `notifications` (+ policy e publication), tabela `house_settings` (+ policy de SELECT por membro) e o bucket público `casasync-media` (pastas avatars/houses/rewards/tasks/suggestions/**messages**). **Exceções pendentes (SQL no topo do `PROJECT_STATUS.md`, aplicar ANTES de subir):** apenas a coluna `tasks.decay_started_at` do decaimento (sem ela, o decaimento cai no fallback `created_at`). As tabelas `achievements`/`dependent_achievements` das conquistas **já foram aplicadas** pelo usuário (ações e rota `/achievements` operacionais). Os blocos de SQL em `PROJECT_STATUS.md` são **registro histórico** do que foi rodado.
- AUTH: sem e-mails reais — contas usam e-mails sintéticos `${username}@admin.casasync` (ADMIN) ou `${username}@dependente.casasync` (DEPENDENT), criadas já `email_confirm: true` via service role; login resolve o username → e-mail sintético e chama `signInWithPassword` pelo cliente do servidor (Server Actions em `src/actions/*.ts`, cada arquivo com `'use server'`).
- Padrão de autorização: SEMPRE derivada da sessão — nunca do input/cliente. O cliente service-role (`createAdminClient`, server-only) é usado para (a) **escritas que o RLS não cobre** (crédito/débito de pontos, criação de usuários) e (b) **leituras cross-role que o RLS não atende**. Nestas, o escopo é sempre explícito e derivado da sessão (`getSessionProfile().user.id`, casa ativa via `getActiveAdminHouse`, `houseId`), **nunca** de parâmetro público.
- **Controle de casa = membresia, não `owner_id`:** o ADMIN controla todas as casas com uma linha `house_members.role='ADMIN'` (criadas E co-geridas via PIN). `getAdminHouses`/`getActiveAdminHouse` e os `assertAdminCanManage` de tarefas/recompensas refletem isso; `houses.owner_id` identifica apenas o tutor/criador.
- Transições de status usam guard condicional (`.eq('status', ...)` / `.in('status', [...])`) para impedir crédito/débito/desaprovação duplicados; falha → rollback. Vale para `COMPLETED → APPROVED` (credita), `PENDING/IN_PROGRESS → APPROVED` (`adminCompleteTask`), `COMPLETED → PENDING` (`rejectCompletedTask`, limpa `completed_by/completed_at`) e `PENDING/IN_PROGRESS → NOT_DELIVERED` (`markTaskNotDelivered`, debita pontos).
- **Prazos de tarefa SEMPRE com fuso:** `<input type="datetime-local">` produz hora local sem fuso; o **cliente** converte para instante via `datetimeLocalToIso` (`src/utils/datetime-local.ts`) antes de chamar as actions, e o **servidor** (`normalizeDueDate` em `src/actions/tasks.ts`) **rejeita** qualquer `due_date` sem designador de zona (`Z`/`±HH:MM`) — uma string naive gravada em `timestamptz` é interpretada como UTC pelo Postgres e desloca o prazo em ~3h (America/Recife). Não "simplificar" convertendo `datetime-local` com `new Date(...)` no envio ou passando a string crua; não mudar `tasks.due_date` para `timestamp`. **Exibir hora local de um instante no JSX sempre renderizado?** use `FormattedDateTime` (`src/components/ui/formatted-date.tsx`) — formatar com getters locais no SSR (Vercel/Netlify = UTC) gera hydration mismatch; nunca soltar `toLocaleString(...)` num card sempre renderizado. Ver seção "Bug de fuso" no `PROJECT_STATUS.md` e **ADR-0013** (`docs/adr/0013-prazos-de-tarefa-com-fuso-horario.md`).
- Realtime: tabelas precisam estar na publication `supabase_realtime`; listeners em `src/hooks/use-postgres-changes.ts` (canal + filter de `house_id` + RLS = isolamento multi-tenant). **Limite:** o browser não usa service role, então Realtime continua sujeito à RLS; leituras service-role não habilitam eventos ao vivo — o `router.refresh()` pós-ação cobre quem age, e policies de SELECT por membro habilitam o cross-role.
- **Realtime + RLS exige `setAuth`:** quando a sessão é restaurada de cookies/storage, o socket Realtime pode conectar como `anon` e o RLS descarta os eventos em silêncio (`SUBSCRIBED` mas zero entregas). O hook `usePostgresChanges` faz `await getSession()` + `await realtime.setAuth(access_token)` **antes** de assinar — nunca remover isso (corrige tarefas, recompensas, resgates, sugestões e notificações de uma vez).

## 4. Regras de negócio críticas
- `user_role`/`member_role` em caixa alta (`ADMIN`/`DEPENDENT`). Hierarquia: Admin → Casa(s) → Dependente(s) → Tarefas/Recompensas, isoladas por `house_id` (RLS) — multi-tenant.
- `ADMIN`: cria/gerencia casas e contas de dependentes (via `createDependent` em `actions/houses.ts`, service role + `email_confirm: true`; DEPENDENT **nunca se cadastra sozinho**), cria/aprova tarefas e recompensas.
- **Reset de senha pelo ADMIN (`updateMemberPassword` em `actions/houses.ts`):** qualquer ADMIN redefine a própria senha; só o **autor da casa (`houses.owner_id`, via `getOwnedHouse`)** redefine a senha de **outros** membros (dependentes ou co-ADMINs) de uma casa que o ator controla — co-ADMIN comum não altera senha de ninguém além da própria. Feito via service role e **sem e-mail**; escopo validado por `house_members` (nunca confia no `targetUserId` do cliente) e senha `>= 6` (`validatePassword`). UI: botão "Senha" (`Key`) nos membros em `houses-manager.tsx` (renderizado só na própria linha ou quando o usuário é o autor da casa ativa), input uncontrolled + feedback inline. Sessões ativas não são revogadas. Ver ADR-0011.
- **Alteração de pontos pelo ADMIN (`updateDependentPoints` em `actions/houses.ts`):** muda o saldo acumulado de um dependente (**SET absoluto**, pode ser negativo) exigindo o **PIN da casa** (`houses.code`, comparado como `joinHouseByPin` — trim + uppercase, fail closed). Valida `validatePoints` (inteiro em `POINTS_MIN/POINTS_MAX`) e que o alvo é `DEPENDENT` de uma casa que o ator controla como ADMIN; escrita em `profiles.points` via service role. UI: pill "N pts" + botão "Pontos" (`Coins`) nos dependentes em `houses-manager.tsx`, campos **uncontrolled** (PIN nunca vai ao estado React) + feedback inline. Ver ADR-0012.
- **Co-controle por PIN:** `houses.code` (único, gerado na criação) é o PIN de convite; outro ADMIN entra com `joinHouseByPin` (`actions/houses.ts`) e passa a controlar a casa junto do dono. A listagem `/dashboard/admin/houses` reflete casas criadas E co-geridas.
- Ciclo da tarefa: DEPENDENT conclui (`COMPLETED`); ADMIN **aprova** (credita pontos) ou **desaprova** (`rejectCompletedTask`: `COMPLETED → PENDING`, limpa a conclusão para o dependente refazer). ADMIN também pode concluir+creditar de uma vez (`adminCompleteTask`).
- **Tarefa "não entregue" (atrasada):** ADMIN marca via `markTaskNotDelivered` (`PENDING/IN_PROGRESS → NOT_DELIVERED`) e **debita** `tasks.points` do dependente (o saldo **pode ficar negativo**). Para o dependente o botão "Concluir" some, mas o pedido de adiamento continua. Aprovar um adiamento (`resolveTaskExtension`) ou alterar o prazo (`updateTask`) **devolve os pontos** e **zera** `tasks.points`: o status volta a ser o equivalente ao novo prazo (futuro → `PENDING`). Não há "Concluir e creditar" para `NOT_DELIVERED`. Ver ADR-0007.
- **Restaurar tarefa aprovada:** ADMIN reaproveita uma tarefa `APPROVED` via `restoreTask` (`APPROVED → PENDING`, guard `.eq('status','APPROVED')`) em vez de criar outra idêntica. Preserva os dados e **não altera os pontos já creditados**; limpa `completed_*`, zera as flags de adiamento e reinicia o prazo para **agora + 1 dia**. Ver ADR-0008.
- **Decaimento de pontos de tarefas (`getTaskCurrentPoints` em `src/utils/task-decay.ts`):** a tarefa perde `pointsPerPeriod` a cada `periodHours` completas desde o **ponto de partida do relógio** — `decay_started_at` (criação ou **última edição**) com fallback `created_at` (tarefas antigas) — com **janela capada no `due_date`** (após o vencimento a perda não cresce) e **piso em 0**. **Adiamentos NÃO reiniciam o relógio** (`resolveTaskExtension`, auto-aceite do `updateTask`, reversão de `NOT_DELIVERED`); `restoreTask` **reinicia** (novo ciclo). `tasks.points` é o **valor-base** intocado; o valor corrente (calculado em runtime) é o usado no **crédito da aprovação** (`approveTask`/`adminCompleteTask`) e no **débito de `NOT_DELIVERED`** (`markTaskNotDelivered`), e as **devoluções** (`resolveTaskExtension` aprovado / `updateTask`) restauram esse mesmo valor corrente (estável para tarefa atrasada — janela capada no prazo). Configurável por casa em `/dashboard/admin/settings` (chave `task_decay`: `enabled`/`periodHours`/`pointsPerPeriod`, defaults 24h/1pt/ativo; `created_at` só opera sem a coluna). A UI mostra o valor corrente (base riscado quando reduzido), exceto em aprovadas (histórico). Ver seção no topo do `PROJECT_STATUS.md`.
- `DEPENDENT`: só vê as próprias tarefas/resgates. Enxerga **todos os tutores** da casa (todos os ADMIN membros, via `getHouseTutors` no dashboard) e o **criador** de cada tarefa (`tasks.created_by`, nome resolvido por `getProfileNames` e exibido nos cards de tarefas).
- **Desativação de recompensa (`setRewardActive` em `actions/rewards.ts`):** ADMIN alterna `rewards.active` (boolean **já aplicado no banco**, default `true` = ativa); recompensa desativada **nunca é excluída**, apenas aparece como **"Indisponível"** no catálogo do dependente e o `requestRedemption` rejeita (`active = false` retorna "Recompensa indisponível no momento."). Só o ADMIN reativa; resgates já aprovados/pendentes não são afetados.
- **Conquistas gamificadas (`/achievements`, ADR-0015):** progresso medido **só em aprovações** (`approveTask`/`adminCompleteTask` → `registerAchievementProgress`, best-effort, nunca derruba o crédito de pontos); `EARNED_POINTS` usa o **valor corrente creditado** (com `task_decay`), sem loop com resgates; `claimAchievementReward` credita `reward_points` **diretamente** em `profiles.points` (repetível: rollover e novo ciclo; não repetível: só nível 1) — e **sem notificação de unlock**. Excluir conquista = avalia cascata do progresso. As 2 tabelas novas **já estão no banco** (aplicadas pelo usuário); restou apenas a coluna `tasks.decay_started_at` do decaimento (SQL no topo do `PROJECT_STATUS.md`).
- Todo novo formulário com campo de senha deve marcar os `<Input>` com `suppressHydrationWarning` (extensões de gerenciador de senhas causam hydration mismatch — já ocorreu em 3 formulários).
- **Credenciais fora do estado React:** senha/`masterPin` NUNCA em `useState`/inputs controlados. Inputs ficam **uncontrolled** (só `name`), lidos via `FormData(event.currentTarget)` no submit e descartados; forms de sucesso chamam `reset()`.
