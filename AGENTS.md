# CasaSync Web — Diretrizes do Projeto

## 1. Comandos de verificação (não há testes configurados)
- `npm run dev` · `npm run lint` (eslint **com `--max-warnings 0`**) · `npm run typecheck` (`tsc --noEmit`) · `npm run build`.
- Ordem antes de entregar: **lint → typecheck → build**. Todos devem passar.
- `npm run lint` deve terminar em **0 warnings** (o script usa `--max-warnings 0`) — nenhum atalho com `eslint-disable` no app. A regra `@next/next/no-img-element` está **desligada no `eslint.config.mjs`** por decisão: as imagens são URLs públicas do Storage (`casasync-media`) e os ícones do app em `public/icons`, então `<img>` é o padrão do projeto (ADR-0005) — não "consertar" trocando por `next/image`. Se surgir um asset realmente otimizável (LCP-crítico), o caminho é `next/image` + `images.remotePatterns` **e** reativar a regra.
- `tsc` depende do gerado `.next/types` (ex: `LayoutProps<"/">` em `src/app/layout.tsx`). Se `.next/` for apagado, rode `npm run build` (ou `next dev`) antes do `tsc` puro.
- **Service worker (`public/sw.js`):** o `fetch` handler faz **cache-first somente para assets estáveis** — `STATIC_ASSETS` (manifest + ícones) e chunks de build sob `/_next/static/` (JS/CSS nomedos por hash). **Qualquer outro GET same-origin passa direto à rede, sem cache** — incluindo os payloads RSC das páginas (o `router.refresh()` pós-ação e o Realtime buscam `/tasks`, `/rewards` etc. com header `RSC:1`). Cachear RSC gravava respostas 200 obsoletas e a UI "piscava" de volta ao dado antigo, demorando a fixar mudanças já gravadas no banco (ver topo do `PROJECT_STATUS.md`). Não re-ampliar o cache-first para navegação nem GETs genéricos; ao trocar o conteúdo do SW, bumpear o `CACHE_NAME` (ex.: `casasync-v4`) para o `activate` limpar caches antigos.
- Rodar `npm run build` antes de `npm run dev` para evitar geração conflitante de `.next`.

## 2. Estrutura e convenções
- Todo o código de app vive em `src/`; alias `@/*` → `./src/*` (tsconfig). Há um route group `(auth)` (URLs `/login` e `/register` sem o prefixo).
- **Next.js 16 trocou middleware por proxy:** a proteção de rotas fica em `src/proxy.ts` (export `proxy` + `config.matcher`, ao lado de `src/app`); a lógica de sessão/role vive em `src/utils/supabase/middleware.ts`.
- `next.config.ts` usa `module.exports` E `export default` (legado com `allowedDevOrigins`). Não "consertar" isso.
- `PROJECT_STATUS.md` é o estado do projeto (requerido ler ANTES de trabalhar e ATUALIZAR ao terminar — funcionalidades, arquivos, decisões, próximo passo).
- Docs complementares (commitados): `docs/schema.md` (snapshot do schema Supabase) e `docs/adr/` (decisões arquiteturais — o "porquê" de padrões como service role/credenciais/proxy/leituras cross-role).
- **Layout widescreen (convenção de grade):** os shells de página (layouts admin/dependente, `/tasks`, `/rewards`, `/achievements`, `/dashboard/admin/settings`, `/dashboard/admin/comunicados` e o header do `DashboardNav`) usam **`max-w-7xl`** (era `max-w-5xl`); telas de auth seguem `max-w-md` (não tocar). Para usar a largura extra, as grades internas ganham colunas por breakpoint **nomeado**: `lg:` (2 colunas), `xl:` (2–5 colunas, catálogos e listas de cards) e grids de formulário continuam em `sm:`/`md:` para não espremer inputs. Em seção que vira 2 colunas, o **heading interno precisa de `xl:col-span-2`** (sem ele o título fica preso na 1ª coluna). **Não usar variantes `2xl:`** — o Tailwind `4.3.3` deste projeto **não emite CSS** para elas (verificado no pipeline real com `@tailwindcss/postcss` e também via `@source inline()`, que já descarta o scanner: `xl:` e `min-[1536px]:` geram, `2xl:` não). Quem precisar do gatilho de 1536px usa `min-[1536px]:`. Para conferir se uma classe entrou mesmo no bundle, buscar o nome escapado (`.xl\:grid-cols-2`) no CSS de `.next/static/chunks/*.css` depois do build — `lint`/`typecheck` **não** pegam classe que não foi gerada.
- **Busca por combinação de palavras no autocomplete de tarefas (ADMIN) — `src/utils/task-normalize.ts`:** o "Você quis dizer..." deixou de ser `includes` do título inteiro e passou a combinar as **palavras** (tags) digitadas, **independente da ordem**, com **no mínimo 1 caractere por palavra** (`MIN_MATCH_WORD_LENGTH = 1` — vale "q" → "quarto"; como atalhos curtos ("o", "e") também contam, quem põe a melhor combinação no topo é a ordenação por qualidade). O termo casa com a palavra do título por **igualdade**, **início** (prefixo: "quar" → "quartos") ou **trecho** ("zin"/"nha"/"ozi" → "cozinha"), com qualidades 3/2/1. Só entra sugestão se **todas** as palavras da busca casarem (`rankTaskTitle` devolve `null` no primeiro termo que falta — senão "varrer sala" puxaria "Varrer a cozinha"), e a ordem vem de `searchTasksByWords`: mais palavra exata > título mais curto > casa mais na frente (≤3 itens, como antes). Módulo **puro e genérico** (`searchTasksByWords<T>(query, items, getTitle, limit)`), sem depender do tipo `Task`; roda **em memória** (o catálogo da casa já está no estado do form — consulta ao banco por tecla só adicionaria latência) e é `useMemo` no `tasks-admin.tsx`. Busca **vazia** é a única que não sugere. O guard de duplicidade (soft block no client + título normalizado no `createTask`) **continua exigindo igualdade** — são duas regras diferentes, não misturar.
- **Castigo do dependente — `dependent_punishments` (SQL em `docs/sql/dependent_punishments.sql`, **aplicado no banco**):** o ADMIN aplica um "castigo" que aparece como **ícone de triângulo ao lado do sino** no header do DEPENDENTE (`/dashboard/dependent`, `/tasks`, `/rewards`, `/achievements`), com `Modal` de leitura mostrando a descrição e a duração informadas pelo tutor. **É SÓ UM INDICADOR:** nenhuma escrita em `profiles.points`/`tasks`/`rewards`/`dependent_achievements` — a penalidade de verdade continua sendo o débito em `updateDependentPoints` (com PIN da casa) e o `NOT_DELIVERED` (ADR-0007/0018); ver **ADR-0020**. Descrição e duração são **OPCIONAIS** (`description` null = modal avisa que não há texto; `duration_days` null = **não expira**, sai só com "Remover castigo"; com 1–365 dias a action grava `expires_at = now + N dias` e a expiração é avaliada na leitura — sem cron). `UNIQUE (profile_id)`: **um castigo ativo por dependente**, e aplicar de novo **substitui** (`upsert`) o anterior. **Sem Realtime** (mesma premissa dos comunicados, ADR-0017) e **sem notificação/push** — castigo é leitura, não evento. Regras puras (validação, `isPunishmentActive`, `punishmentExpiryFromNow`, `punishmentDurationLabel`, tipo `ActivePunishment`) em **`src/utils/punishments.ts`** (módulo puro, importado pelo client); leitura `getActivePunishment(profileId, houseId)` (`React.cache` + service role, com **limpeza lazy** do vencido) e **`getHouseActivePunishments(houseId)`** (devolve os castigos ativos **com descrição/duração/vencimento** — um caminho único para a tela do ADMIN) em **`src/utils/active-punishment.ts`**; actions **`applyPunishment`/`removePunishment`** em `src/actions/punishments.ts` (recebem **só o `profileId`** — a casa vem de `getActiveAdminHouse`, e o alvo precisa ser `DEPENDENT` dela; qualquer ADMIN da casa ativa pode, inclusive co-ADMIN, porque punição é rotina). UI: botão **"Castigo"** (`TriangleAlert`, âmbar quando ativo) na linha do `DEPENDENT` em `houses-manager.tsx` + `PunishmentIndicator` no `DashboardNav` (prop `punishment`, só DEPENDENT). **O modal do ADMIN mostra o castigo ATUAL** (bloco de leitura: descrição — ou "sem descrição" —, duração e vencimento em `FormattedDateTime`) e os campos de descrição/duração são **controlados, inicializados do castigo atual** (ao abrir o modal): salvar nunca apaga o texto já escrito por engano, e "Remover castigo" limpa os campos. A visão geral do ADMIN (`/dashboard/admin`) **não tem cards "Tarefas"/"Recompensas"** (ficam só Casas, Configurações, Comunicados — grade `sm:grid-cols-2 lg:grid-cols-3`); essas telas continuam na nav. `expelMember`/`deleteDependentAccount`/`deleteHouse` removem os castigos no fluxo explícito.
- **Limite de adiamentos por tarefa (implementado — SQL em `docs/sql/task_extension_count.sql`, **ainda NÃO aplicado no banco**):** novo campo **`maxExtensions`** na chave `extension_rules` (0 = ilimitado, default preserva o comportamento atual) no card "Adiamento de tarefas"; limita quantas vezes o prazo da **mesma tarefa** pode ser esticado. **Nova coluna `tasks.extension_count`** — não existia histórico (as flags de `extension_requested`/`extension_reason` são do pedido **atual**, então não dá para saber quantos adiamentos a tarefa já teve); tarefas existentes nascem em `0` e a dica da tela avisa que a regra vale daqui pra frente. **O contador soma na APROVAÇÃO** (`resolveTaskExtension`), não no pedido — **recusar não estica prazo** e não pode consumir o orçamento do dependente; **não contam** editar o prazo direto no card, `restoreTask` nem a reativação de `ON_HOLD` (são decisão do ADMIN, que sempre pode mudar o prazo direto). A trava fica no pedido do dependente (`requestTaskExtension`) com mensagem acionável, e o ADMIN pode aprovar um pedido feito antes de a casa baixar o limite. UI: o banner do pedido mostra "N de M" (só quando há limite) e o update otimista soma o contador na hora. **Corrigida uma corrida no mesmo caminho:** `resolveTaskExtension` fazia `update().eq('id', taskId)` **sem guarda de estado**, então dois cliques em "Aprovar (+N dias)" aplicavam o adiamento **duas vezes** (e somariam o contador duas) — ganhou `.eq('extension_requested', true)`, a mesma defesa de transição guardada do resto do app. **Ordem obrigatória: SQL antes do deploy** (o app lê a coluna e quebraria com `column does not exist`). Injeções best-effort: `approveTask`/`adminCompleteTask` → `TASKS_APPROVED` (1) + `EARNED_POINTS`; `rejectCompletedTask` → `TASKS_REJECTED`; `approveRedemption` → `REWARDS_CLAIMED`; `resolveRewardSuggestion` aprovado → `CUSTOM_REWARDS_APPROVED`; `registerLoginDay` (`src/actions/stats.ts`, 1×/dia em America/Recife, idempotente, streak) nos renders dependentes p/ `APP_LOGIN_DAYS`/`STREAK_LOGIN_DAYS`. Métricas: **8** (`TASKS_APPROVED`, `TASKS_REJECTED`, `REWARDS_CLAIMED`, `CUSTOM_REWARDS_APPROVED`, `APP_LOGIN_DAYS`, `STREAK_LOGIN_DAYS`, `EARNED_POINTS`, `MANUAL`) — a antiga `COMPLETED_TASKS` foi renomeada (migração no SQL). **`adjustAchievementProgress(achievementId, profileId, amount=1)`** só ADMIN, exige conquista `metric_type='MANUAL'` da casa ativa e membro DEPENDENT (`amount` inteiro **com sinal**, `≠ 0`, `|amount|` ≤ 1000) — **positivo concede, negativo retira** (revisão do tutor): `progress = max(0, atual − |amount|)` com **piso 0** e, ao cair abaixo do objetivo, o `unlocked_at` é **limpo** (desbloqueio revogado, o dependente não consegue mais resgatar; chega via Realtime de `dependent_achievements`); retirar exige progresso existente (sem linha/0 → erro, não cria linha zerada) e o **`level` nunca muda** (é histórico de resgates) — o ajuste é **escopado à conquista escolhida** (5º param `onlyAchievementId` de `syncAchievementProgress`): um `+1`/`−1` **não** mexe nas outras `MANUAL` da casa, ao contrário das métricas automáticas (uma ocorrência conta para todas com a mesma métrica) — UX: botões **"+1"/"−1"** por dependente em `/achievements` (ADMIN; o "−1" só aparece com progresso e desliga em 0) e um "zerar contagem" (`RotateCcw`, com `Modal` de confirmaão), com resposta **imediata**: a action **relê e devolve a linha gravada** (`data.progress`) e a UI aplica **otimista + reconciliação** (rollback por snapshot em erro) — sem `router.refresh` e sem depender do Realtime, que nem sempre entrega o próprio write; **`claimAchievementReward`** só DEPENDENT da própria casa, credita em `profiles.points` o valor do **nível atual** (`achievementRewardAtLevel`), repetível **zera o `current_progress`** (ciclo novo exige o objetivo inteiro de novo — a trava do ADR-0019) e sobe 1 nível por ciclo até `max_level` (cap continua repetível) e não repetível resgata só no nível 1). **Decisões de escopo:** progresso conta apenas aprovações (não débitos); `EARNED_POINTS` conta só créditos de tarefa aprovada (sem loop com resgates); **notificação `ACHIEVEMENT_UNLOCKED` no desbloqueio** (dependente **e** ADMINs da casa, autor excluído dos ADMINs — emitida por `syncAchievementProgress`/`notifyUnlocked` quando o `unlocked_at` passa de `null` para preenchido, em qualquer métrica: automática ou ajuste manual); conquista `is_secret` aparece como card oculto "Conquista secreta" (sem título/descrição/ícone próprios) e **revela individualmente** — só no desbloqueio **daquela** conquista (`unlocked_at` da linha do dependente, ou `level > 1` se já foi resgatada); "ter linha de progresso" NÃO revela, porque `syncAchievementProgress` cria linha para todas as conquistas da métrica (inclusive as secretas). UI: `achievements/achievements-admin.tsx` (CRUD + progresso por dependente **sempre visível** — sem toggle de expandir/colapsar; abrir o form por "Editar"/"Nova" faz `scrollIntoView` + foco no título via `formRef`/`titleRef`; chips de ícone + `ImageUpload` de imagem + campos nível máximo/multiplicador; **sem `router.refresh`** — Realtime cobre), `achievements/achievements-dependent.tsx` (barra/pill "N/N" + nível/máx + recompensa do nível atual — **métrica e multiplicador não aparecem para o dependente**; título em destaque `text-base font-bold`; `handleClaim` otimista + `router.refresh()`), `achievements/achievement-icon.tsx` (`AchievementIcon` + `ICON_MAP`). **Item "Conquistas" da nav dourado quando há resgate disponível:** predicado único puro **`isAchievementClaimable(progress, isRepeatable)`** (`src/utils/achievements.ts`: desbloqueado **e** não resgatado — repetível → basta `unlocked_at`; única → só `level === 1`), usado nos cards do dependente, no servidor (`hasClaimableAchievement(profileId)` cached em `src/utils/achievement-progress.ts` = 1 query das linhas desbloqueadas + 1 da `is_repeatable` das conquistas envolvidas) e na nav; `DashboardNav` recebe `hasClaimableAchievement?: boolean` (**só DEPENDENT** — ADMIN nunca dourado) e pinta o item `/achievements` de âmbar (condicionais via `cn`, com prioridade sobre o item ativo). **Instantâneo via store de aba** (`src/hooks/use-claimable-achievement.ts` — `useSyncExternalStore` + `setClaimableAchievements`): o `AchievementsDependent` publica o valor derivado a cada mudança (resgate otimista + Realtime) porque é **irmão** da nav na page; a prop do servidor realinha o store na navegação. Nav ganhou o item **"Conquistas"** (`Trophy`) — ADMIN passa a **5** itens, DEPENDENT mantém **4** (o slot extra da bottom nav só existe com `< 4` itens). Limpeza: excluir conquista apaga o progresso (FK cascade); `expelMember`/`deleteDependentAccount`/`deleteHouse` removem linhas de `dependent_achievements` (e `deleteHouse` as `achievements` da casa). Ver seção no topo do `PROJECT_STATUS.md` (SQL aplicado — registro histórico) e **ADR-0015**/**ADR-0016**.
- **Comunicados/avisos da casa — rota `/dashboard/admin/comunicados` (módulo com 2 tabelas `comunicados` + `comunicado_deliveries` — SQL em `docs/sql/comunicados.sql`, **já aplicado no banco pelo usuário**; **não há nada pendente**):** o ADMIN cria avisos para a casa ativa (título 1–120, descrição **30**–500 — mínimo de 30 caracteres, `repeats_total` 1–100, `repeat_interval_days` 0–365, `repeat_weekdays` int[] default todos, `repeat_time` **`time` default `'08:00'`** — agendamento em **America/Recife**) e publica (`published`). **SEM tempo real (decisão de produto) para COMUNICADOS:** o comunicado só aparece no **render server-side** das telas do dependente — ao **atualizar a página, trocar de endpoint** ou após confirmar; o overlay não tem subscription de `comunicados` (a única剩下 no módulo é a do `comunicados-admin.tsx`, tela de gestão do ADMIN). **Penalização é a exceção:** a fila dela nasce no render (notificações não lidas) e acompanha o Realtime de `notifications` (filter `recipient_id`) no mesmo overlay. **1ª exibição em "slot de hoje ou próximo"** (não é imediata nem espera o dia seguinte na maioria dos casos): num **dia agendado**, se o horário de hoje **já passou** o aviso aparece já no **próximo render**; se **ainda não chegou**, espera o **horário de hoje**; em dia **não agendado**, aparece no **próximo dia agendado**. O **intervalo de repetição não conta** nesse primeiro ciclo. **Repetição POR DEPENDENTE**: cada confirmação agenda a próxima ocorrência (`last_confirmed_at`, somando o intervalo em dias, corta para o próximo weekday agendado e aplica o horário, helpers puros em **`src/utils/comunicados.ts`** — `recifeWeekday`/`nextComunicadoOccurrence`/`toDueComunicado`/`comunicadoSchedule`, módulo sem `'use server'`); ao completar `repeats_total` para de aparecer. **Sem cron** — o gatilho agendado é cálculo server-side na leitura. Overlay **bloqueante único** do dependente (`src/components/alerts/alert-queue-overlay.tsx`, portal `z-[120]` — acima do `Modal` z-[100]): **comunicados publicados e alertas de penalização na MESMA fila, uma-a-uma em FIFO por `created_at` — a penalização NÃO tem prioridade** (a antiga `penalty-dialog.tsx` foi removida; agora ela também cobre `/tasks` e `/rewards`, onde antes não aparecia), foco preso no campo de confirmação, **Esc bloqueado** (capture), scroll travado; alimentado por `getDueComunicados()` + notificações não lidas **no render** (props: `userId`/`initialQueue`/`initialNotifications`), confirmado sai da fila na hora (estado local, sem esperar round-trip). **Comprovação de leitura do comunicado:** confirmar exige **≥ 3 palavras do próprio aviso** (título ou descrição, qualquer ordem, sem diferenciar caixa/acento, repetidas não contam, termo de 1 caractere ignorado) — predicado puro `matchedAlertWords` em `src/utils/alert-queue.ts` habilita o botão na UI e **o servidor revalida** em `confirmComunicadoDelivery(id, typedPhrase)` (fail closed). A penalização só precisa de "Entendi" (`markNotificationRead`). Actions em `src/actions/comunicados.ts` (CRUD ADMIN + `getDueComunicados` + `confirmComunicadoDelivery`; `assertAdminCanManage` da casa ativa, validação fail-closed — descrição 30–500 com `.trim()`). **`comunicado_deliveries` fica FORA da publication e sem policies client** (service-role; total do ADMIN atualiza via `revalidatePath`/`router.refresh()` pós-ação — sem Realtime). Sem item na nav (ADMIN continua 5 itens) — acesso pelo card "Comunicados" na visão geral. Limpeza: `deleteComunicado` remove as deliveries (FK cascade); `deleteHouse` remove os comunicados (FK cascade em `comunicados`). Ver **ADR-0017**.
- **Configurações da casa (ADMIN) — rota `/dashboard/admin/settings` + card na Visão geral:** tabela `house_settings` (PK `house_id,key`, `value` jsonb), escrita **exclusivamente** por `updateHouseSettings` (`src/actions/settings.ts`, service role + membresia ADMIN) e lida pelos getters cached em `src/utils/house-settings.ts` (`getHouseRewardPricingSettings`/`getHouseQuickMessageSettings`/`getHouseTaskSlaSettings`/`getHouseExtensionRulesSettings`/`getHouseNotificationRetentionSettings`/`getHouseNotificationMuteSettings`/`getHouseTaskDecaySettings`/`getHouseTaskRulesSettings`, fallback aos defaults de `src/utils/settings.ts`). **Sem Realtime** — a propagação depende do `router.refresh()` pós-ação (e das revalidações de `/tasks`, `/rewards`, `/dashboard/dependent` quando `quick_message` muda, e de `/tasks` quando `task_sla`/`extension_rules`/`task_decay`/`task_rules` mudam). As configurações alimentam: `approveRedemption` (toggle + faixas do encarecimento em `nextRewardCost` — chave `reward_pricing`); a mensagem rápida (`sendQuickMessage` valida maxChars/capacity; `cleanupQuickMessages` usa `settings.readRetentionDays`; o compositor e a plumbagem bell→nav usam `QuickMessageSettings`, carregada nos call sites DEPENDENT — chave `quick_message`); os prazos de tarefas (`restoreTask`, o prefill do form e o autocomplete usam `defaultDueDays`; o chip "Prazo próximo" de ADMIN/dependente usa `dueSoonHours` — horas restantes até o prazo, limiar absoluto, passado como prop pelas páginas — chave `task_sla`); o adiamento (os botões "Aprovar (+N dias)" renderizam `dayOptions` e `resolveTaskExtension` **rejeita dias fora da lista**; `maxExtensions` limita quantas vezes a MESMA tarefa pode ser adiada (checado no pedido do dependente, somado na aprovação) — chave `extension_rules`, ver §2 e o ADR-0022); a retenção de notificações comuns (`cleanupReadNotifications` aplica `readRetentionDays` **por casa da notificação**, excluindo `QUICK_MESSAGE` — chave `notification_retention`); e o **decaimento de pontos de tarefas** (`enabled`/`periodHours`/`pointsPerPeriod` — chave `task_decay`; ver §4 "Decaimento de pontos"). As chaves novas `notification_mute` (silenciar categorias, guardado no `notifyUser`/`notifyHouse`) e `task_rules` (teto de pontos e limite de tarefas ativas, guardado em `createTask`/`updateTask`) entram pelo mesmo caminho — ver §2 e a Etapa 1 do `PROJECT_STATUS.md`. Não repassar chaves de settings por parâmetro público — a leitura é sempre derivada da casa da sessão.

## 3. Supabase
- Três clientes em `src/utils/supabase/`: `server.ts` (`createClient`, regras Servers/RSC), `client.ts` (`createClient` browser), `admin.ts` (`createAdminClient` com service role, **server-only** — nunca importar de client component).
- Env vars só em `.env.local` (nomes exatos, `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` — é *publishable*, não `ANON_KEY` — `SUPABASE_SERVICE_ROLE_KEY`, `MASTER_PIN` que valida o cadastro de ADMIN em `actions/auth.ts`); `.env*` está no `.gitignore`, nada disso vive no repo. **Não existe `PIN_PTS`:** a alteração manual de pontos (`updateDependentPoints`) é validada pelo PIN da casa (`houses.code`).
- **Migrações SQL não estão no repo:** a pasta `supabase/` não existe e `supabase/*.sql` é gitignore. Mudanças de schema são aplicadas manualmente no dashboard do Supabase — sem aplicá-las, features falham em runtime. **Tudo já foi aplicado no banco:** colunas de imagem (incluindo `rewards.active` e `notifications.image_url`/`message_id` da mensagem rápida), `reward_suggestions`, flags `extension_*`, enum `task_status` com `NOT_DELIVERED`/`ON_HOLD`, tabela `notifications` (+ policy e publication), tabela `house_settings` (+ policy de SELECT por membro), bucket público `casasync-media` (pastas avatars/houses/rewards/tasks/suggestions/**messages**), **`tasks.decay_started_at`**, as **3 colunas das conquistas** (`image_url`/`max_level`/`level_multiplier`), as tabelas **`achievements`**/**`dependent_achievements`** e a tabela **`dependent_stats` + migração `COMPLETED_TASKS→TASKS_APPROVED`** e a tabela **`dependent_punishments`** (castigo do dependente) — **nada pendente no banco**, **exceto a coluna `tasks.extension_count` (limite de adiamentos, ver §2 e o ADR-0022), que ainda NÃO foi aplicada**. Os blocos de SQL em `PROJECT_STATUS.md` são **registro histórico** do que foi rodado.
- AUTH: sem e-mails reais — contas usam e-mails sintéticos `${username}@admin.casasync` (ADMIN) ou `${username}@dependente.casasync` (DEPENDENT), criadas já `email_confirm: true` via service role; login resolve o username → e-mail sintético e chama `signInWithPassword` pelo cliente do servidor (Server Actions em `src/actions/*.ts`, cada arquivo com `'use server'`).
- Padrão de autorização: SEMPRE derivada da sessão — nunca do input/cliente. O cliente service-role (`createAdminClient`, server-only) é usado para (a) **escritas que o RLS não cobre** (crédito/débito de pontos, criação de usuários) e (b) **leituras cross-role que o RLS não atende**. Nestas, o escopo é sempre explícito e derivado da sessão (`getSessionProfile().user.id`, casa ativa via `getActiveAdminHouse`, `houseId`), **nunca** de parâmetro público.
- **Controle de casa = membresia, não `owner_id`:** o ADMIN controla todas as casas com uma linha `house_members.role='ADMIN'` (criadas E co-geridas via PIN). `getAdminHouses`/`getActiveAdminHouse` e os `assertAdminCanManage` de tarefas/recompensas refletem isso; `houses.owner_id` identifica apenas o tutor/criador.
- Transições de status usam guard condicional (`.eq('status', ...)` / `.in('status', [...])`) para impedir crédito/débito/desaprovação duplicados; falha → rollback. Vale para `COMPLETED → APPROVED` (credita), `PENDING/IN_PROGRESS → APPROVED` (`adminCompleteTask`), `COMPLETED → PENDING` (`rejectCompletedTask`, limpa `completed_by/completed_at`) e `PENDING/IN_PROGRESS → NOT_DELIVERED` (`markTaskNotDelivered`, debita pontos), `{PENDING,IN_PROGRESS,NOT_DELIVERED} ↔ ON_HOLD` (`setTaskOnHold`, sem mexer em saldo) e `{ON_HOLD} → PENDING` com prazo/decay novos (reativação).
- **Prazos de tarefa SEMPRE com fuso:** `<input type="datetime-local">` produz hora local sem fuso; o **cliente** converte para instante via `datetimeLocalToIso` (`src/utils/datetime-local.ts`) antes de chamar as actions, e o **servidor** (`normalizeDueDate` em `src/actions/tasks.ts`) **rejeita** qualquer `due_date` sem designador de zona (`Z`/`±HH:MM`) — uma string naive gravada em `timestamptz` é interpretada como UTC pelo Postgres e desloca o prazo em ~3h (America/Recife). Não "simplificar" convertendo `datetime-local` com `new Date(...)` no envio ou passando a string crua; não mudar `tasks.due_date` para `timestamp`. **Exibir hora local de um instante no JSX sempre renderizado?** use `FormattedDateTime` (`src/components/ui/formatted-date.tsx`) — formatar com getters locais no SSR (Vercel/Netlify = UTC) gera hydration mismatch; nunca soltar `toLocaleString(...)` num card sempre renderizado. Ver seção "Bug de fuso" no `PROJECT_STATUS.md` e **ADR-0013** (`docs/adr/0013-prazos-de-tarefa-com-fuso-horario.md`).
- Realtime: tabelas precisam estar na publication `supabase_realtime`; listeners em `src/hooks/use-postgres-changes.ts` (canal + filter de `house_id` + RLS = isolamento multi-tenant). **Limite:** o browser não usa service role, então Realtime continua sujeito à RLS; leituras service-role não habilitam eventos ao vivo — o `router.refresh()` pós-ação cobre quem age, e policies de SELECT por membro habilitam o cross-role.
- **Realtime + RLS exige `setAuth`:** quando a sessão é restaurada de cookies/storage, o socket Realtime pode conectar como `anon` e o RLS descarta os eventos em silêncio (`SUBSCRIBED` mas zero entregas). O hook `usePostgresChanges` faz `await getSession()` + `await realtime.setAuth(access_token)` **antes** de assinar — nunca remover isso (corrige tarefas, recompensas, resgates, sugestões e notificações de uma vez).

## 4. Regras de negócio críticas
- `user_role`/`member_role` em caixa alta (`ADMIN`/`DEPENDENT`). Hierarquia: Admin → Casa(s) → Dependente(s) → Tarefas/Recompensas, isoladas por `house_id` (RLS) — multi-tenant.
- `ADMIN`: cria/gerencia casas e contas de dependentes (via `createDependent` em `actions/houses.ts`, service role + `email_confirm: true`; DEPENDENT **nunca se cadastra sozinho**), cria/aprova tarefas e recompensas.
- **Reset de senha pelo ADMIN (`updateMemberPassword` em `actions/houses.ts`):** qualquer ADMIN redefine a própria senha; só o **autor da casa (`houses.owner_id`, via `getOwnedHouse`)** redefine a senha de **outros** membros (dependentes ou co-ADMINs) de uma casa que o ator controla — co-ADMIN comum não altera senha de ninguém além da própria. Feito via service role e **sem e-mail**; escopo validado por `house_members` (nunca confia no `targetUserId` do cliente) e senha `>= 6` (`validatePassword`). UI: botão "Senha" (`Key`) nos membros em `houses-manager.tsx` (renderizado só na própria linha ou quando o usuário é o autor da casa ativa), input uncontrolled + feedback inline. Sessões ativas não são revogadas. Ver ADR-0011.
- **Alteração de pontos pelo ADMIN (`updateDependentPoints` em `actions/houses.ts`):** muda o saldo acumulado de um dependente (**SET absoluto**, pode ser negativo) exigindo o **PIN da casa** (`houses.code`, comparado como `joinHouseByPin` — trim + uppercase, fail closed). Valida `validatePoints` (inteiro em `POINTS_MIN/POINTS_MAX`) e que o alvo é `DEPENDENT` de uma casa que o ator controla como ADMIN; escrita em `profiles.points` via service role. UI: pill "N pts" + botão "Pontos" (`Coins`) nos dependentes em `houses-manager.tsx`, campos **uncontrolled** (PIN nunca vai ao estado React) + feedback inline. Ver ADR-0012.
- **Co-controle por PIN:** `houses.code` (único, gerado na criação) é o PIN de convite; outro ADMIN entra com `joinHouseByPin` (`actions/houses.ts`) e passa a controlar a casa junto do dono. A listagem `/dashboard/admin/houses` reflete casas criadas E co-geridas.
- Ciclo da tarefa: DEPENDENT conclui (`COMPLETED`); ADMIN **aprova** (credita pontos) ou **desaprova** (`rejectCompletedTask`: `COMPLETED → PENDING`, limpa a conclusão para o dependente refazer). ADMIN também pode concluir+creditar de uma vez (`adminCompleteTask`).
- **Tarefa "não entregue" (atrasada):** ADMIN marca via `markTaskNotDelivered` (`PENDING/IN_PROGRESS → NOT_DELIVERED`) e **debita** `tasks.points` do dependente (o saldo **pode ficar negativo**). Para o dependente o botão "Concluir" some, mas o pedido de adiamento continua. **A penalidade é DEFINITIVA:** aprovar um adiamento (`resolveTaskExtension`) ou alterar o prazo (`updateTask`) **reabre** a tarefa mas **não devolve** os pontos — só zera `tasks.points` e ajusta o status ao novo prazo (futuro → `PENDING`). Não reintroduzir o `adjustPoints` positivo nem o rollback de reembolso nos dois fluxos (seria brecha pela edição direta do prazo). Não há "Concluir e creditar" para `NOT_DELIVERED`. Ver ADR-0007 (emenda 2026) e **ADR-0018**.
- **Tarefa em espera (`setTaskOnHold` em `src/actions/tasks.ts`, status `ON_HOLD`, novo no enum — SQL em `docs/sql/task_on_hold.sql`, **aplicado no Supabase**):** ADMIN pausa uma tarefa **aberta ou não entregue** (`PENDING/IN_PROGRESS/NOT_DELIVERED`, guard `.in('status', …)`) e a tarefa **some da lista do dependente** (filtro `.neq('status','ON_HOLD')` em `/tasks`): nada de "Concluir"/"Pedir mais tempo", `updateTask` **edita normalmente** (pausa não congela edição — só a visibilidade), o pedido de adiamento pendente é descartado e, se era `NOT_DELIVERED`, entra **valendo 0** (consequência da penalidade definitiva). Reativar (`onHold: false`, guard `.eq('status','ON_HOLD')`) volta **sempre** para `PENDING` com **prazo novo** (agora + `task_sla.defaultDueDays`) e **decaimento reiniciado** (mesmo ciclo do `restoreTask`), preservando `tasks.points` e sem tocar no saldo. UI ADMIN: botão "Colocar em espera" no card pendente (também no `NOT_DELIVERED`) + seção "Em espera" com "Voltar para pendente" sempre visível e **campos editáveis no card em espera** (título/descrição/pontos/responsável com debounce; o **prazo não** é campo — a reativação sempre o recalcula, então aparece como texto "Prazo atual (temporário)"); notificação ao dependente nos dois sentidos (`TASK_ON_HOLD` / `TASK_RESTORED`). `expelMember`/`deleteDependentAccount` apagam `ON_HOLD` como tarefa ativa. Não alterar `dependent_stats` (pausar não é aprovar nem rejeitar). Ver **ADR-0018**.
- **Restaurar tarefa aprovada:** ADMIN reaproveita uma tarefa `APPROVED` via `restoreTask` (`APPROVED → PENDING`, guard `.eq('status','APPROVED')`) em vez de criar outra idêntica. Preserva os dados e **não altera os pontos já creditados**; limpa `completed_*`, zera as flags de adiamento e reinicia o prazo para **agora + 1 dia**. Ver ADR-0008.
- **Decaimento de pontos de tarefas (`getTaskCurrentPoints` em `src/utils/task-decay.ts`):** a tarefa perde `pointsPerPeriod` a cada `periodHours` completas desde o **ponto de partida do relógio** — `decay_started_at` (criação ou **última edição**) com fallback `created_at` (tarefas antigas) — com **janela capada no `due_date`** (após o vencimento a perda não cresce) e **piso em 0**. **Adiamentos NÃO reiniciam o relógio** (`resolveTaskExtension`, auto-aceite do `updateTask`, reversão de `NOT_DELIVERED`); `restoreTask` **reinicia** (novo ciclo). `tasks.points` é o **valor-base** intocado; o valor corrente (calculado em runtime) é o usado no **crédito da aprovação** (`approveTask`/`adminCompleteTask`) e no **débito de `NOT_DELIVERED`** (`markTaskNotDelivered`), e as **devoluções** (`resolveTaskExtension` aprovado / `updateTask`) restauram esse mesmo valor corrente (estável para tarefa atrasada — janela capada no prazo). Configurável por casa em `/dashboard/admin/settings` (chave `task_decay`: `enabled`/`periodHours`/`pointsPerPeriod`, defaults 24h/1pt/ativo; `created_at` só opera sem a coluna). A UI mostra o valor corrente (base riscado quando reduzido), exceto em aprovadas (histórico). Ver seção no topo do `PROJECT_STATUS.md`.
- `DEPENDENT`: só vê as próprias tarefas/resgates. Enxerga **todos os tutores** da casa (todos os ADMIN membros, via `getHouseTutors` no dashboard) e o **criador** de cada tarefa (`tasks.created_by`, nome resolvido por `getProfileNames` e exibido nos cards de tarefas).
- **Desativação de recompensa (`setRewardActive` em `actions/rewards.ts`):** ADMIN alterna `rewards.active` (boolean **já aplicado no banco**, default `true` = ativa); recompensa desativada **nunca é excluída**, apenas aparece como **"Indisponível"** no catálogo do dependente e o `requestRedemption` rejeita (`active = false` retorna "Recompensa indisponível no momento."). Só o ADMIN reativa; resgates já aprovados/pendentes não são afetados.
- **Conquistas gamificadas (`/achievements`, ADR-0015 + ADR-0016):** progresso **derivado de `dependent_stats`** (e somado no crédito p/ `EARNED_POINTS`); injeções best-effort nas ações (`approveTask`/`adminCompleteTask` → `TASKS_APPROVED`+`EARNED_POINTS`, `rejectCompletedTask` → `TASKS_REJECTED`, `approveRedemption` → `REWARDS_CLAIMED`, `resolveRewardSuggestion` aprovado → `CUSTOM_REWARDS_APPROVED`, `adjustAchievementProgress` p/ `MANUAL`; `registerLoginDay` nos renders dependentes), nunca derruba o crédito de pontos; `EARNED_POINTS` usa o **valor corrente creditado** (com `task_decay`), sem loop com resgates; **`resetAchievementProgress` (`MANUAL`) zera a contagem** do dependente (`current_progress = 0` + `unlocked_at` limpo = revoga desbloqueio não resgatado, `level` preservado) com as mesmas guardas do ajuste e exige progresso existente; `claimAchievementReward` credita `reward_points` **diretamente** em `profiles.points` **pelo nível atual** (`reward_points × nível × level_multiplier`), repetível sobe 1 nível/ciclo até o cap (trava no `max_level` e segue pagando a recompensa máxima) e não repetível só no nível 1 — com **notificação de unlock** (dependente + ADMINs, autor excluído). **"Há resgate disponível?"** é o predicado único puro `isAchievementClaimable` (`src/utils/achievements.ts`), e o item "Conquistas" da nav fica **dourado** para o DEPENDENT enquanto houver (store de aba em `src/hooks/use-claimable-achievement.ts` → instantâneo no resgate). Excluir conquista = avalia cascata do progresso (e remove a `image_url` do storage, best-effort). **Todo o SQL das conquistas já está no banco** (aplicado pelo usuário): as 2 tabelas, as 3 colunas (`image_url`/`max_level`/`level_multiplier`), a tabela `dependent_stats` e a migração `COMPLETED_TASKS→TASKS_APPROVED` (registro no topo do `PROJECT_STATUS.md`).
- Todo novo formulário com campo de senha deve marcar os `<Input>` com `suppressHydrationWarning` (extensões de gerenciador de senhas causam hydration mismatch — já ocorreu em 3 formulários).
- **Credenciais fora do estado React:** senha/`masterPin` NUNCA em `useState`/inputs controlados. Inputs ficam **uncontrolled** (só `name`), lidos via `FormData(event.currentTarget)` no submit e descartados; forms de sucesso chamam `reset()`. Server Actions de credencial não podem lançar exceção não tratada (o Next sobreporia overlay de dev com os argumentos) — use try/catch e retorne `ActionResult` (`ok:false` + mensagem genérica).
