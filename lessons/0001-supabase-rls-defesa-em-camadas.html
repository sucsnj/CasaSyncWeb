0001 — Supabase: defesa em camadas

Por que CasaSync usa utils/supabase/server.ts + Row Level Security — e como isso impede um Dependente da Casa A de ver Tarefas da Casa B.

O que você leva desta lição

  • Entender que chamada de banco no servidor tem dois guardrails: o cliente SSR (quem você é) e a RNL (o que você pode enxergar) — e por que o segundo é o que de fato impede vazamento.
  • Conseguir explicar o truque do ?houseId=B que não leak de capacidade.
  • Escrever uma Server Action de busca de tarefas limpa e segura.

1. Por que o helper utils/supabase/server.ts?

O Supabase não é chamado "direto" das páginas. Toda query que um Server Component faz precisa saber de quem é a sessão daquele request. Isso vem dos cookies. O @supabase/ssr entrega createServerClient, que é genérico de framework — ele pendura o cookie adapter em cada request:

export async function createClient() {
  const cookieStore = await cookies()
  return createServerClient<Database>(URL, KEY, {
    cookies: {
      getAll() { return cookieStore.getAll() },
      setAll(cookiesToSet) {
        try {
          cookiesToSet.forEach(async ({ name, value, options }) =>
            cookieStore.set(name, value, options))
        } catch { /* Server Component não grava cookie: Proxy faz isso */ }
      },
    },
  })
}

Isso importa porque:

  • Identidade por request. O cliente do servidor "é basicamente um fetch configurado"; precisa ser recriado a cada request com os cookies daquele request. Quem compartilha cliente entre requests acaba vendo a sessão de outra pessoa — os docs do pacote chamam isso de "random logouts e sessões terminadas cedo".
  • Refresco de token. Quando o token expira, o SDK chama setAll para gravar o token refeito. Server Component não pode gravar cookie — por isso o try/catch ignora o erro. Quem grava de verdade é o Proxy (proxy.ts → updateSession), que roda antes da renderização, refresha com auth.getUser() e repassa o cookie no response.
  • Key publishable, nunca service role. O helper usa NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY. Com o JWT da sessão, o PostgREST executa a query como authenticated — e RNL se aplica. A SUPABASE_SERVICE_ROLE_KEY ignora RNL; por isso mora em utils/supabase/admin.ts e é server-only.
Regra do projeto: Server Component / Server Action / Route Handler só tocam banco por createClient() de @/utils/supabase/server. Client Component usa @/utils/supabase/client (createBrowserClient). Quem cria o helper centraliza cookie, tipagem e env vars num único lugar — DRY + impossível esquecer o adapter.

2. RNL: por que o ID jogado na URL não vaza a Casa B

O navegador nunca fala com o banco diretamente. Ele envia HTTP ao PostgREST com Authorization: Bearer <JWT>. Antes de qualquer SQL, o PostgREST valida a assinatura do token. Então a política RNL roda com auth.uid() — que lê o claim sub verificado. Não é "o que o usuário disse", é "quem o servidor reconheceu".

Agora o ataque: Dependente da Casa A abre a URL trocando o ID — ?houseId=B, ou POSTa { "taskId": "…da Casa B" }. O que muda é apenas qual linha ele pediu. O que não muda é quem ele é (vem do JWT, que ele não consegue forjar). A política RNL é uma condição sobre a linha, avaliada pelo banco:

create policy "dependente vê tarefas somente da própria casa"
on public.tasks for select to authenticated
using (
  house_id in (
    select house_id from public.house_members
    where profile_id = (select auth.uid())   -- escopada ao usuário atual
      and role = 'DEPENDENT'
  )
);

Para a Casa B, auth.uid() não pertence a nenhuma membership daquele house_id → a condição é falsa → Postgres retorna 0 linhas. Um SQL perfeitamente válido que pedia a Casa B simplesmente não devolve nada.

A armadilha clássica: subquery de membership sem escopo por auth.uid() (ex.: house_id in (select distinct house_id from house_members)) parece escopar, mas devolve as casas de todos os usuários — vaza tudo. O padrão seguro exige where profile_id = (select auth.uid()) dentro da subquery. E não use claims de autorização em user_metadata: o próprio usuário consegue editá-las via SDK.

3. Server Action limpa: autorização da sessão + RNL como backstop

'use server'

import { createClient } from '@/utils/supabase/server'
import type { ActionResult } from './types'

type Task = {
  id: string
  title: string
  reward_points: number
  due_date: string | null
}

export async function fetchMyTasks():
  Promise<ActionResult & { data?: Task[] }> {

  const supabase = await createClient()   // identidade vem da sessão

  const { data: { user } } = await supabase.auth.getUser()
  if (!user) return { ok: false, error: 'Não autenticado.' }

  // Escopo derivado no servidor — o navegador não envia house_id.
  const { data: membership } = await supabase
    .from('house_members')
    .select('house_id')
    .eq('profile_id', user.id)
    .maybeSingle()

if (!membership)
    return { ok: false, error: 'Conta não vinculada a uma casa.' }

  // RNL é o backstop: mesmo que este filtro sumisse, o banco veta a Casa B.
  const { data, error } = await supabase
    .from('tasks')
    .select('id, title, reward_points, due_date')
    .eq('house_id', membership.house_id)
    .eq('assigned_to', user.id)
    .order('due_date', { ascending: true })

  if (error) return { ok: false, error: 'Falha ao carregar tarefas.' }

  return { ok: true, data }
}

Note as três camadas, em ordem de menor para maior confiança:

  1. Identidade — user.id sai do JWT verificado (getUser()), nunca de argumento chamado pela UI.
  2. Escopo explícito — house_id e assigned_to são derivados no servidor da membership daquela sessão.
  3. Backstop — a política RNL aplica a mesma condição no banco. Se você tirar a camada 2 por engano, o vazamento continua bloqueado; se a RNL tiver a armadilha da seção 2, nenhuma camada de código conserta.
Tradução para o projeto: isso já vive no seu código. Veja actions/create-dependent.ts:27-52 — sessão → user_role → membership → ação. A próxima etapa (tarefas/recompensas) segue exatamente a mesma sequência com fetchMyTasks como template.

Verifique o que ficou (recall)

Tente responder antes de abrir as respostas. Cada opção tem o mesmo tamanho — não use a formatação como pista :)

1. O que define, no banco, quais linhas você consegue enxergar?
  • A política RNL
  • O ID enviado
  • A minha senha
  • A tabela usada

Resposta: A política RNL

Por quê: o ID na URL só escolhe qual linha pedir; a RNL decide o conjunto de linhas que a sua sessão pode ver. Por isso trocar ?houseId=B por si só não vaza nada.

2. De onde vem o auth.uid() usado na política?
  • Do JWT verificado
  • Do input cliente
  • De um cookie
  • Do banco central

Resposta: Do JWT verificado

Por quê: o PostgREST valida a assinatura do token antes do SQL e o sub verificado alimenta auth.uid(). É valor que o cliente não consegue forjar — exatamente o que torna o ataque de troca de ID ineficaz.

Para fixar de verdade

  1. Revise utils/supabase/server.ts e proxy.ts e identifique as três responsabilidades: criar cliente por request, adapter de cookies, refresh no Proxy.
  2. Escreva a policy da seção 1 no seu projeto e teste autenticado como um usuário da Casa A pedindo loop pela Casa B — deve vir vazio (HTTP 200 com [], não erro).
  3. Refatore: mude fetchMyTasks para aceitar houseId do navegador e verifique que, com RNL correta, continua seguro — e então reverta, porque derivar no servidor é mais limpo.
