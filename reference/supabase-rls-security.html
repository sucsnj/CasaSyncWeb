Referência rápida — Segurança Supabase (RNL + Cliente SSR)

Princípio: autorização vem da sessão verificada no servidor, nunca do input do navegador. A RNL é a última linha de defesa — o veto no banco, independente do caminho do app.

1. Como cada papel é executado

2. Por que o helper utils/supabase/server.ts

  • Liga o cliente à sessão do request atual via cookies (getAll/setAll). Cliente novo por request — nunca global.
  • setAll grava refresh de token; em Server Component falha e é ignorado no try/catch — o Proxy (proxy.ts) faz o refresh e repassa o token refeito.
  • Usa a publishable key: toda query roda como authenticated → RNL aplicada.
  • Centraliza tipagem Database, env vars e o "cola" frágil de cookies em um só lugar.

3. RNL: por que manipular IDs não vaza nada

-- pipeline de cada request
navegador → PostgREST valida assinatura do JWT → RNL usa auth.uid() = sub verificado
→ usuário trocou ?houseId=B? Política filtra → 0 linhas, nunca dados da Casa B.
  • auth.uid() lê o claim verificado do JWT; não é client-asserted.
  • Política multi-tenant correta: subquery de membership SEMPRE escopada por profile_id = (select auth.uid()).
  • Perf: escreva (select auth.uid()) — initPlan calcula uma vez por statement.

4. Armadilhas comuns (checklist)

  • RNL desativada em tabela nova → exposta ao anon.
  • Policy sem referência a auth.uid()/auth.jwt() em subquery → vaza tenant.
  • Claim de autorização em user_metadata → usuário altera o próprio papel.
  • service_role no bundle client → RNL eliminada (tudo exposto).
  • Testar RNL pelo SQL editor = inútil (é superuser, ignora RNL). Teste autenticado.
  • UPDATE sem WITH CHECK → usuário move linha para outro tenant.

5. Esqueleto de policy segura (tasks)

create policy "vê tarefas só da própria casa"
on public.tasks for select to authenticated
using ( house_id in (
  select house_id from public.house_members
  where profile_id = (select auth.uid())
    and role = 'DEPENDENT' ) );

Se house_members tiver RNL própria, pode haver recursão — nesse caso envie via função security definer em schema privado com set search_path=''.

6. Server Action — forma "defesa em camadas"

1º) Sessão via createClient() → identidade. 2º) Escopo derivado no servidor (membership). 3º) RNL como backstop do filtro. O navegador nunca envia house_id nem decide a quem pertence a linha.
